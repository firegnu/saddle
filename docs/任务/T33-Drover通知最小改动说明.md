## 用户已确认的方向

- 只在关键节点弹提示，持续待处理事项使用现有 Attention。
- saddle Settings 选择 `System` 或 `In saddle`。选择内部提示后，saddle 没运行时不回退系统通知；下次打开仍能查看尚未处理的事项，不承诺离线事件补发。
- Hammerspoon 的限流／上下文／用量提醒原样保留；CCNotify 已按另行授权清理，与本次 Drover 改动无关。
- 用户担心 Drover 的改动影响任务运行，因此先核实能否仅改通知层。

## 建议的最小边界

Drover 仅负责自己的系统通知开关与通知去重；saddle 从已有公开任务状态生成内部提示。Drover 不读取 saddle 配置，不调用 saddle，不增加连接、重试投递、通知接收服务或对 corral／分派技能的新依赖。

首版弹出事件限于「任务完成、等待放行」。主控 idle 且判据未满足不再自动弹，保留其公开 attention／看板状态，saddle 如需汇总仍走已有公开查询。这是通知筛选变化，不是删除任务状态或改完成判据。

## 拟议公开接口（名称及语义待核实，不是已有命令）

候选形式：`drover notifications status --json`、`drover notifications on --json`、`drover notifications off --json`。如有更符合 Drover 的最小形式，由 Drover 主控建议。

- 拟按本机当前用户、跨登记项目生效；不绑定调用者 cwd，不要求目标项目先 init。这个作用范围须在 Settings 明示，避免误认为只控制当前项目。
- 状态读取只读；开启／关闭只改变通知偏好，不改变队列、暂停、loop 或 gate。持久化由 Drover 自己管理，saddle 只通过公开 CLI 操作，不能直读内部文件。
- 建议这份通知偏好作为唯一事实来源：Settings 读到开启时显示 System，关闭时显示 In saddle；不在 saddle config 再保存一个容易矛盾的副本。新配置缺失时建议保持系统通知开启，错误读取要明确返回不可用，不能伪装成关闭。
- 写操作需返回实际生效状态；失败时 Settings 不宣称保存成功。运行中的引擎在后续通知检查中读取偏好，不要求用户启停服务切换。切换生效边界由 Drover 主控明确。

## 去重和切换需要核实的边界

- 同一次任务运行不因刷新、原因文案变化、短暂观察缺失而重复弹；不能只按 T 编号或项目显示名识别。核实已有公开字段能否稳定区分项目及任务运行，历史字段缺失时明确降级，不猜。
- 通知开关应与“用户已处理”分开：关闭系统通知不能放行任务、清除 Attention 或改历史结果。
- 系统渠道与内部渠道各自观察同一任务，二者没有天然共享的已提示记录。需要提出最小、可解释的切换／重启基线规则；不要为了去重引入跨程序消息系统。首次启用是否提示当前已有 awaiting，以及切换渠道是否再次提示，留作明确决策，不默认承诺零重复／零漏报。
- 开关保存时可能已有系统通知发送在途；核实生效时点及可保证的边界，不把“命令成功”误写成“已撤回 OS 中的旧横幅”。旧版 Drover 不支持接口时，Settings 必须显示不支持，不能假装静音成功。
- 多个 saddle 实例读到同一个全局偏好时，内部提示如何归属尚未决定；属于 saddle 侧待定项，不让 Drover承担 UI 实例路由。
