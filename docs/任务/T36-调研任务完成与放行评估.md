# T36：调研任务完成与放行评估

2026-09-28，saddle/main。用户最新指示：「开始吧，通过这个任务看看到底怎么做是最好的」。这取代任务正文中“不立即调研”的入队说明，本轮仅评估，不实现、委派或推进真实队列。核对基线：saddle `ea267c2`、Drover `46d7699`。方案经用户回复「可以的」确认；本轮只定稿设计，具体公开契约及实施安排尚未启动。

## 结论

建议保留现有自动完成检查，新增一个明确的人工入口：**人工确认完成（Mark complete manually…）**。它用于用户已经验收成果、但 Git 完成条件不适用的任务；成功后只进入现有 Awaiting release，仍由用户另行放行。不要首版新增一个直接完成、放行并可能连带推进下一项的“强制放行”按钮，也不要先引入研究／开发任务类型系统。

对调研任务，用户验收报告本来就是合理的正常完成方式，不应要求为了通过队列门槛而合并文档、造代码提交或删除保留分支。开发任务仍默认按现有自动检查完成；人工入口也可以处理用户明确接受的例外，但必须如实记录为人工确认，不能写成检查全部通过。

## 现状与 T33 原因

- saddle `src/queue.rs` 的 Check & release / g 发出 `Operation::Go`；`src/drover.rs::Operation::args` 仅调用公开 `drover go`。没有另一套完成判据，也没有强制参数。
- Drover `bin/drover::cmd_go` 在 current 存在时先走 `record_done` → `check_done`；检查成功后才记录 done 和 go。若已有 awaiting，则只记录 go，不重新检查。go 自身不调用 next；loop 开着时，引擎可能随后派下一项。
- `check_done` 检查已跟踪文件是否有未提交修改、main 是否前进、候选分支是否合入，以及项目 CHECK_CMD。收尾记号缺失不会单独阻挡手工 go，但会阻挡引擎自动确认。
- `bin/drover-board::criteria / task_branches` 以分支是否包含任务起点 SHA 推断候选，无法知道一个分支属于“保留研究”还是“必须合入的实现”。任务正文写“只调研、不合并”不会改变它。
- T33 的公开检查记录明确只有 branches_merged 不满足；不是用户点错按钮。详见同目录 `T33-系统通知收敛调研.md` 最后的归档记录。
- 现有 `drop` 是放弃，历史状态为 dropped，不能代替调研完成。手工改内部事件、临时删分支躲检查或伪造收尾也不建议采用。

## 方案比较

| 方案 | 效果与代价 | 建议 |
| --- | --- | --- |
| 调研报告一律合入 main 后按现有流程收尾 | 不改程序；适合本就需要入库的报告，但不能覆盖无仓库产物或明确要求保留分支的调研 | 可选工作方式，不设为强制规则 |
| 新增研究／人工验收任务类型 | 能事前表达完成方式，但要改变入队编辑、类型存储、自动循环、展示和旧任务兼容 | 首版暂不做 |
| 新增强制完成并放行 | 一步解除阻塞，但混合“成果已验收”和“允许继续”，loop 开启时可能很快派下一项 | 不作为首选 |
| 新增人工确认完成，复用普通放行 | 明确记录人工验收，保留完成／放行两阶段，避免改变开发任务的自动规则 | 推荐 |

人工完成适合报告已读、咨询已结束、成果无需 Git 合并等情况；不适合仅因 agent 暂时 idle、测试耗时或不知道是否完成就自动触发。无需按标题猜“调研”或要求先更改任务类型。

## 建议交互与操作语义

入口放在 Tasks 中当前进行中任务的详情操作区域，与既有项目级 Check & release 区分；只绑定该任务，不随选中历史条目作用到另一个任务。使用次要按钮 `Mark complete manually…`，不新增易误触的单键快捷键。

点击后打开一次确认弹层：项目、任务编号／标题、自动检查当前结果（含未运行或不可用），再填一行原因，例如“调研报告已审阅，研究分支按约定保留”。确认文案明确“以人工验收记为完成，仍等待放行；不会合并、删除分支或停止 agent”。取消不写入。已处于 Awaiting release 的任务继续使用正常放行，不需要此入口。

建议人工完成覆盖业务上的自动完成依据：main 未前进、分支未合入、缺少收尾记号、工作区有未提交修改、CHECK_CMD 未执行或失败，都可以由用户看清后明确接受。原结果必须保留为未满足／未运行／失败，不改成通过；不为确认动作再次启动整套 CHECK_CMD。工作区有修改时只说明并保留，不提交、清理或丢弃它们。

**不能覆盖操作本身失败**：无法可靠读取项目／当前任务、任务身份已变、事件写入失败等，应拒绝操作，不能用“强制”吞掉错误。公开身份须绑定具体运行（不只任务编号）；确认前后目标变了就刷新，不能顺势完成下一项。公开检查不可用也不能假装成功；Git 检查不适用可由用户确认，但当前任务身份或状态不可确定时必须停住。

无论项目 gate 设置如何，人工完成都固定停在 Awaiting release，不调用 go／next、不改变 loop／pause 设置。已记录完成后继续使用原放行入口；用户放行后，loop 开启项目仍可能自动推进，界面沿用现有说明。这保证新增动作本身不派下一项，并复用现有 Attention 和任务完成通知，不保证“放行以后仍不推进”。

## 改动归属与最小接口

- **Drover 必须改**：新增一个公开人工完成操作（命令名称与参数待其主控确认），绑定项目和任务运行身份；记录 done 时保留人工确认方式、原因、确认时间和当时检查结果／未执行状态，固定进入待放行。list／show 公开返回该标记，历史能区别自动检查与人工验收；旧历史无法确定的不要倒填“自动通过”。既有自动检查和 go 默认行为保留，自动引擎不得调用人工覆盖路径。
- **saddle 必须改**：Tasks 的入口／确认弹层、公开命令调用、身份过期及错误反馈、详情里的人工确认标记。只显示 Drover 返回的判断，不复制 Git 检查，不读写其内部文件。旧 Drover 不支持时明确提示，不能回退为偷偷调用普通 go 或改内部记录。
- **corral 无需改**；首版不需要修改全局 corral-dispatch 技能，不要求新建任务类型或分支归属协议。若某项目 AGENTS 明确强制所有研究分支合并，则另行澄清该项目规则，不能由新按钮暗中改写。
- 若用户确认实施，先由 Drover 主控核实最小公开契约及事件兼容，再做 saddle 消费方。此时才按仓库流程确定实现／审查安排；本轮不发咨询或派实现者。

这是跨两仓库的中等改动，主要难点是正确记录人工验收和确认目标，不是按钮本身。不能按“只加一个按钮”估算，也无需顺带重构 Drover 核心。

## 保留分支的后续影响

人工确认不是 Git 清理：保留研究分支仍可能被之后的开发任务检查算入，尤其下一任务与本任务起点相同、main 没有前进时。这是现有分支归属推断的局限，新入口不能宣称一并解决。

对确实要保留的研究成果，收尾时应明确后续保存方式；报告是否入库、研究分支是否长期保留仍听用户决定。不要自动删除、隐藏或永久忽略该分支来通过检查。本轮不扩展为“按任务登记所有分支”的新协议；若之后频繁阻塞，结合 T31 并行任务评估单独讨论，而非把全部复杂性塞进强制按钮。
