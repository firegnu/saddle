# T33：agent 系统通知收敛到 saddle 的调研报告

日期：2026-09-28。性质：仅调研，方案待用户决定；没有实施或切换通知渠道。

## 1. 结论

可以让 saddle 成为 agent 通知的统一展示入口，但目前的通知分散在 **Drover、Hammerspoon 菜单栏监控、agent 自身及终端宿主**，不是 saddle 的一个开关。只给现有 Attention 加自动弹窗，既不能阻止外部系统通知，也不能覆盖它们全部的触发条件。

本机查明的主要情况如下。这里的“已配置”指磁盘配置和引用代码，不等于实际横幅已送达；本轮没有发送通知或读取通知历史。

| 来源 | 当前证据等级 | 通知内容／去向 | 对收敛的影响 |
| --- | --- | --- | --- |
| Drover 独立 `loop` 引擎 | 发送链与本机 LaunchAgent 配置已确认；引擎实时运行、OS 送达未确认 | 主控停下而判据未满足；任务做完待放行 → `osascript` → macOS | 需要处理 Drover 的发送策略；项目 `loop=false` 不等于关通知 |
| Hammerspoon 菜单栏监控 | 当前配置包含发送分支，Hammerspoon 进程存在；内存加载版本及送达未确认 | 进入 RateLimited、context ≥85%、5h／周用量 ≥80% → `hs.notify` → macOS | 这些指标不在 corral／Attention 当前数据中；要保留它们，需要额外接入 |
| Claude CCNotify | Stop／UserPromptSubmit hook 已配置；Stop 发送调用已注释，Notification hook 未配置 | 脚本仍具备 `terminal-notifier` 能力，但已查到的 hook 链没有调用它发通知 | 不能把“安装了 CCNotify”认定为当前完成横幅来源 |
| Codex 外部 `notify` | 用户配置已启用，目标可执行文件存在；目标内部行为未确认 | 调用 Computer Use 的 `SkyComputerUseClient turn-ended` | 不能未经确认就替换：它可能还承担客户端回合结束集成 |
| Codex TUI → 宿主终端 | 官方能力已确认；本机未显式设置 TUI 通知字段，逐进程生效值未确认 | 回合结束／审批请求可经 OSC 9 或 BEL 发出 | 与外部 `notify` 是两条渠道；不能只改其中一条便声称全部收敛 |
| Herdr | 本机配置明确 `ui.toast.delivery="herdr"` | 当前配置选择 Herdr 内部 toast；`system`／`terminal` 是另外的可选能力 | 当前不能把它的 toast 当作 macOS 通知；如果也要统一内部提示，应另计范围 |
| corral / corral-dispatch | 查到状态采集 hook；未发现内核或该技能直接调用桌面通知发送器 | `Notification` 事件用于状态机；旧 `tools/board --bell` 可响铃 | 保留状态采集；不能为了静音而删除 corral hooks |

依据分别见下文 S1–S13。建议用户先决定收敛哪些通知、saddle 不可用时如何处理，再决定采用观察状态还是接收来源事件的方式。**完整覆盖已发现来源会涉及 saddle 以外的代码／配置；没有证据表明必须先修改 corral 内核。**

## 3. 来源、触发条件与调用链

### 3.1 Drover：通知不受项目 loop 开关直接控制

实际源码调用链：[S1](#s1-drover-发送器)、[S2](#s2-drover-事件判定)。

```text
drover loop
  └─ cmd_loop_run → tick
       ├─ B.loop_tick：推进启用了 loop 的项目
       └─ 每至少 60 秒 collect(登记项目)
            → project_state → add_waits → wait_items
            → notify_new → osascript -e 'display notification ...'
```

`cmd_loop_run` 默认常驻；`tick` 的通知分支独立调用 `B.collect`，后者没有按项目 `loop` 开关筛选。因此“loop=false，所以不会收到 drover 通知”不成立。`--once` 也会进入这条链，本轮没有运行它，因为它同时可能推进真实任务。

通知有两类：

1. `stop`：有当前任务，主控状态 idle 至少 120 秒、最近输入来源不是 `agent`，且收尾标记／Git 判据仍有明确不满足项。此处 `do_check=False`，不执行验收命令。它是 Drover 的“需要人看看”推断，不是 agent 真正完成的声明。
2. `release`：任务已记录完成且正在等待放行。消息提示用户放行；发送通知本身不执行放行。

`add_waits` 明确不再另报主控 blocked，原因是 corral 看板已经显示。它也不是对所有子 agent 的普通回合结束都发通知。

发送标题为 `drover · <项目> 等你`，一个项目合并为一条，正文第一项／新增数量压成单行并截到 220 字符。去重 key 含项目名、类型及原因文本等；当前事项解决后会从去重集合消失，重现可再提醒。源码使用 `~/.drover/board-notified.json`，本轮只读到了这个路径定义，未打开该文件。发送返回码未作为成功条件，发送失败也可能被记录为已通知，不能把它当作可靠投递日志。

本机 `~/Library/LaunchAgents/dev.drover.loop.plist` 配置了 `~/.local/bin/drover loop`、`RunAtLoad=true`、`KeepAlive=true`，未设置 `DROVER_NOTIFY_BIN`。[S3](#s3-drover-本机启动配置) 代码默认 `NOTIFY_BIN="osascript"`。这证明已经安装自动启动配置，不证明 launchd 当时已加载或引擎仍存活；公开 drover CLI 没有本轮可用的投递状态查询。

`DROVER_NOTIFY_BIN` 是替换外部可执行文件的入口，传入的是 `-e` 和 AppleScript 文本，不是结构化业务事件。可以研究适配，但不建议把反解析 AppleScript 当长期协议；也不能通过停掉整个 loop 引擎达到“只切换通知”的效果。

### 3.2 Hammerspoon：目前菜单栏监控发的是异常提醒

CCNotify 注释提到“menubar agents viewer”，继续追踪定位到 `~/.hammerspoon/init.lua`。[S4](#s4-hammerspoon-配置与来源) 当前代码链为：

```text
3 秒定时器（无 session 时 15 秒）
  → ~/.cargo/bin/abtop --json
  → sessions → notifyTransitions
  → rate_limits / Claude 用量缓存补充 → notifyLimits
  → hs.notify.new(...):send() → macOS 通知中心
```

`hs.notify` 的系统通知语义由 [Hammerspoon 官方文档](https://www.hammerspoon.org/docs/hs.notify.html)确认。Hammerspoon 进程存在，但本轮没有重新加载配置、调用刷新函数或发送探针，不能保证运行中的 Lua 恰好与磁盘版本一致。

当前磁盘代码的触发条件：[S5](#s5-hammerspoon-触发与去重)。

- 会话首次观察后，状态跃迁到 `RateLimited`，发“被限流”，声音 Basso。
- 会话状态为 Thinking／Executing／Waiting，且 context 从未超线变为 ≥85%，发 context 提醒，声音 Glass；Done／Unknown 不触发这一类。
- Codex／Claude 各自 5h、周用量从未超线变为 ≥80%，发用量提醒，声音 Sosumi。过期窗口的百分比先作废。
- 首个快照只建立基线，不补发；以 session ID（缺失时 PID）／来源与窗口记录边沿，内存去重，重载不提供历史回放。
- 普通 Waiting 只在菜单栏计数和展示；当前代码没有对它或普通 Done 发系统通知。CCNotify 的旧注释不足以证明现在还发“等待输入”横幅。

通知点击动作是打开监控窗口的 `toggle`，不是 saddle 跳转。Claude 用量补充函数引用 `~/.cache/ccstatusline/usage.json`；只读了函数代码，没有读缓存或调用获取用量的接口。abtop 可执行文件存在；本轮未验证其数据准确性、上游采集实现或会话与 corral instance 的映射。因此不能假设这些通知全都对应当前 corral 管理的 agent。

### 3.3 Claude：配置着 CCNotify 不等于它还在发完成通知

`~/.claude/settings.json` 中：[S6](#s6-claude-配置及-ccnotify)。

- `Stop` → `~/.claude/ccnotify/ccnotify.py Stop`。
- `UserPromptSubmit` → 同一脚本的 UserPromptSubmit。
- 当前全局及本轮检查的项目配置中没有 CCNotify 的 `Notification` hook，未见 `disableAllHooks` 开启。

脚本 `handle_stop` 仍更新本地跟踪数据，但第 144–150 行的 `self.send_notification(...)` 被整段注释。`handle_notification` 中保留权限／选择类通知能力，最终会运行 `terminal-notifier`，却没有在已查到的配置中接入；其 Waiting 分支本来还会抑制发送。UserPromptSubmit 只记录输入，不是通知发送点。脚本没有在本轮被执行。

Claude 的 `Notification` 是 hook 事件名称，不能据此直接认定 macOS 横幅。corral 启动 Claude 时追加的 Notification hook 指向 corral 自己的事件采集器，而不是 CCNotify。[Claude 官方 hook 文档](https://code.claude.com/docs/en/hooks#notification)也将该 hook 描述为可用于转发的事件接口。

配置另有 `agentPushNotifEnabled=true`。本轮官方 settings-reference 页面抓取失败，未据第三方解释断定其目的地，也未确认账户／客户端实际生效情况；它不能作为“macOS 完成横幅已启用”的证据。未检查独立 Claude 桌面应用的偏好、管理配置、会话级覆盖或全部插件 hook，不能宣称全机 Claude 来源已排除。

### 3.4 Codex：外部 notify 与终端通知必须分开

用户 `~/.codex/config.toml:19` 的 `notify` 指向 Computer Use 应用内的 `SkyComputerUseClient`，参数为 `turn-ended`；目标文件存在。[S7](#s7-codex-通知配置) OpenAI 官方文档区分了两条通路：[外部 notify 与 TUI 通知](https://learn.chatgpt.com/docs/config-file/config-advanced#notify-vs-tuinotifications)、[字段参考](https://learn.chatgpt.com/docs/config-file/config-reference#configtoml)。

- 外部 `notify` 调用程序并传 JSON。本机配置可证明会接入这个程序，但没有该程序内部调用链或逐进程有效配置证据，不能断定它必然显示系统横幅，也不能断言删掉只影响横幅。
- `tui.notifications` 管终端界面的通知，可按 `agent-turn-complete`、`approval-requested` 等事件过滤；`notification_method` 有 auto／osc9／bel。当前官方文档说明 auto 优先 OSC 9、必要时退回 BEL，并有 unfocused／always 条件。

本机 `[tui]` 没有显式的上述通知字段。corral 的 Codex adapter 追加 lifecycle hooks 和 hook trust 启动参数，没有设置 `notify` 或 TUI 通知开关；配置继承、启动覆盖及运行版本仍可能影响具体进程，不能仅凭全局文件宣称每个 Codex 都在发某一种通知。[S8](#s8-corral-采集与状态语义)

`~/.codex/hooks.json` 目前仅有 SessionStart 的 Herdr 元数据／会话绑定 hook；`features.hooks=true`。配置里的 `hooks.state` 历史信任项不等于这些事件 hook 现在都启用，不能把它当当前发送器清单。

### 3.5 终端、Herdr 与 corral：相邻能力不是同一件事

- Ghostty 当前官方 [desktop-notifications 配置](https://ghostty.org/docs/config/reference#desktop-notifications)支持将 OSC 9／777 转为系统通知。已找到的本机 Ghostty 配置没有相关显式覆盖；未核实运行版本、启动参数或 OS 权限，因此这里只确认通路能力。BEL 的声音／Dock 提醒和桌面横幅也不能混称。没有发送任何控制序列探针。
- Saddle 的 PTY 数据经过 `Screen::process` 解析再渲染，事件处理只返回 PTY 写入／尺寸／颜色查询，其余分支忽略；当前不是把子终端原始字节一律透传给外层终端。不能假设 Codex 的 OSC／BEL 在 saddle 内一定到达 Ghostty，也不能用拦截这些字节覆盖外部进程直接发出的 OS 通知。[S9](#s9-saddle-终端与控制接口)
- Herdr 本机选择内部 toast：`delivery="herdr"`、延迟 1 秒、右下角。已安装 0.9.1 changelog 说明 system 模式可用 macOS `terminal-notifier`／`osascript`，terminal 模式可交给外层终端，内部模式不额外转发桌面通知；这些是可选能力，当前配置并未选择它们。SessionStart 脚本负责 `pane.report_agent_session`，本身没有桌面通知调用。[S10](#s10-herdr)
- corral `hook.py` 收集生命周期事件；`events.py` 将 PermissionRequest、permission_prompt 归为 blocked，将 Stop／StopFailure／Interrupt 归为 idle。普通 idle 不等于整项任务完成；`Notification` 事件也不是 corral 发桌面通知的函数。[S8](#s8-corral-采集与状态语义)
- corral 旧 `tools/board --bell` 可在观察到回合结束或进入 blocked 时 `curses.beep()`，是可选终端响铃；未确认有运行实例。已检查的 corral／corral-dispatch 技能没有直接调用桌面发送器的要求；任务派发／结果回传不是这个系统通知链。[S11](#s11-旧看板及技能)

## 4. 与现有 Attention 的关系

Attention 是“现在有哪些事项需要看”的清单，需要手动按 `a` 或点击打开；系统通知是“某次事件发生时提醒”的投递行为。两者可以共用条目身份和跳转，但不能直接视为等价。[S12](#s12-attention-设计和代码)

| 现有事项 | Attention 当前行为 | 替代外部通知时的缺口 |
| --- | --- | --- |
| corral blocked／错误／来源读取失败 | Needs attention，持续状态仍在就保留 | 尚无自动 toast；瞬时状态可能在轮询间发生又消失 |
| 本次运行观察到新一轮结束 | New replies；同一 agent 与等待／错误合并 | 是观察推断；不是可靠逐事件回放，不等于任务 done |
| Drover 等待放行／历史失败 | 跨登记项目汇总；历史失败可 Mark seen | 和 release 部分重叠；仍需切换旧发送器防重复 |
| Drover 主控 idle 且判据未满足 | 全局 Attention 当前没有汇总 | 当前 Surveyor 只取 `drover list --json`；该快照不带 show 的 attention |
| Hammerspoon 限流／context／用量阈值 | 没有这些条目／数据 | corral 当前公开元数据不提供这些指标 |
| 未经 corral 管理的 agent | 不在当前 agent 列表 | 来源覆盖和会话身份需要另定，不能用项目名猜 agent |

`src/agents.rs::absorb` 用相同 instance 的 working→idle 或 `turn_started` 变化标未读；首次出现不补标，同名换 instance 清掉旧未读，选中／正在展示的 agent 清未读。失败已看和未读均不跨重启持久化。通知如果复用这些状态，必须明确首屏是否只建基线、已看与处理完成的区别；不能弹一次就把仍在 blocked／待放行的事项消除。

Drover 已有公开 `show Tn --json --with-agent-status`，能返回 `attention.state=suggested`、`reason=idle_with_unmet_criteria`、结构化 `unmet_rows`。Saddle 任务详情已经使用它，可以作为进一步汇总的候选，**不需要去读 `.drover.conf` 或从 why 文案反推逻辑**。[S13](#s13-drover-公开-attention-与-saddle-调用)

但 `show_attention` 与旧通知的 `wants_human` 并非完全同一实现：前者按明确 MAIN_AGENT 查询、处理缺失字段／unavailable，并依据详情 completion rows；后者还有按 cwd 寻主控的回退及自身判据组合。若要求原通知精确保真，需在 Drover 侧统一判定或增加公开结构化出口，不能宣称“直接读 show 就百分之百复现旧通知”。

## 5. 可选方案与建议范围

以下均为建议，不构成设计定案或实施授权。目标应是将各来源的提醒投递给 saddle，而不是从 macOS 通知中心读取／截获历史。

### 方案 A：Saddle 观察公开状态，生成内部提醒

复用 corral 轮询、跨项目 list 和必要的 show 数据，在条目新出现／状态变化时显示短提示，点开现有 Attention／目标终端／任务详情。优点是核心输入已有公开接口，普通等待、回复、放行可较小范围完成。

限制是轮询可能丢掉瞬时事件，不覆盖 Hammerspoon 指标、非 corral 会话及未确认客户端通知，也不解决外部发送器继续弹的问题。来源静音／路由配置仍需另做。若用户只选择这些基本提醒，才可以把第一阶段主要功能限定在 saddle；不能将它称作全部系统通知已收敛。

### 方案 B：来源保持判定，统一投递到 Saddle（覆盖完整来源时优先评估）

给 saddle 增加受约束的公开通知接收方式，保留现有 Attention 作为查看与处理入口。Drover、Hammerspoon 等来源把已判定的事件交给这个接口，在目标实例接收成功后按所选策略停止同一事件的系统横幅；对来源不明的 Codex 客户端先补齐调用链，再决定是否适配。

当前 `ctl` 只有 Inspect／Request／Open／Close，没有 Notify 操作；它不会仅改调用命令就自动获得接收通知能力。[S9](#s9-saddle-终端与控制接口) 是否复用这个传输、另设入口或采用小型本地适配器，应在正式设计时决定。

| 部位 | 可能所需改动 | 可以保留的边界 |
| --- | --- | --- |
| saddle | 内部 toast、来源与事件去重、目标跳转、接收结果；若采用外部事件，还要接收接口和实例路由；必要时汇总 Drover suggested | 继续使用公开 corral／drover 数据；查看不自动回答或放行 |
| Drover | 可选投递目的地／失败策略；完整语义需要统一判定或提供结构化事件；明确定义去重何时算投递成功 | 不改变队列推进和完成判据，不停整个 loop 来静音 |
| Hammerspoon／通知适配器 | 将三类 `hs.notify` 出口路由到 saddle；补来源身份、阈值事件标识、目标不可用处理 | 可保留菜单栏和现有采集；不必要求 saddle 读取会话历史／用量凭证 |
| corral | 方案 A 可沿现有 ls/status；基本收敛不要求修改内核。只有需要公开稳定事件序号、回放或新的身份映射时再评估扩展 | 生命周期 hook 和真实状态不能因静音被关闭 |
| Codex／Claude 配置与脚本 | 经确认后调整对应通知出口；Codex 外部 notify、TUI 和客户端集成分别处理 | 不整体关闭所有 hook；CCNotify 当前已静音的 Stop 无须为了“关通知”再改 |
| 终端／Herdr | 仅当用户要纳入它们的重复通路时调整相关配置 | 不通过全局关闭 OS 应用权限处理特定 agent 通知 |
| 技能 | 只有新增“明确业务里程碑”通知职责才补说明；也可只记部署／使用方法 | 不要求每个 agent 靠自然语言记得手动发通知来保证可靠性 |

正式设计至少要回答：事件来源、唯一身份和目标是什么；同名重启／任务号跨项目怎样区分；多个 saddle 实例由谁接收；接收确认与用户已看如何分开。针对来源重试和 Attention 轮询的重复应使用结构化身份合并，不依靠正文相同。context／用量指标应保留“来源报告的指标”语义，不能变造成 corral blocked。

建议提示采用不抢输入焦点的短 toast，提供跳到 Attention／目标的动作，重要事项留在可回看的入口。具体位置、时长、声音、是否汇总连发，以及等待／完成哪些级别自动弹，均待用户决定，不在本报告补成验收要求。

## 6. Saddle 未运行、不可见或重启时

| 策略 | 行为与代价 |
| --- | --- |
| 只在 saddle 内显示 | 没有接收实例就没有即时提醒。下次启动只能重建仍在公开状态里的事项；普通回复、短暂错误、已经回落的阈值不能保证补齐 |
| saddle 接收优先，不可用时保留原系统通知 | 较容易保留现有提醒能力，建议优先让用户比较；必须定义超时／失败是否回退、由谁回退以及如何去重。不能只检查进程存在就认定通知已收到 |
| 离线保存，启动后补发 | 需要来源 outbox 或常驻接收服务、持久化／过期／消费规则，是额外范围；当前 Attention 没有这项保证，不建议默认加上 |

“saddle 正在运行”和“用户看得到 saddle”不同：窗口最小化、终端失焦、在别的 tab、多实例都可能让内部提示不可见。要不要这时也保留 OS 横幅，必须由用户决定。仅凭 `SADDLE_INSTANCE` 启动环境也不能自动覆盖早于 saddle 创建、在其他终端创建的 agent；没有唯一接收目标时，不能随意选第一个实例或全广播。

采用任何方案都应先证明所选事件在新入口可定位、重复行为可解释，再按来源切换。后续若实施，需要另行授权以合成事件验证并决定是否做真实通知验证；本轮没有切换或探针发送。
