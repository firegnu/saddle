## 已有事实与需谨慎表述的地方

## 当前主控判断（供质疑，不是定案）

1. 目标应围绕“任务过程档案与复盘”，不要为追求完整原始遥测反过来扩大核心工具改动。
2. 候选思路：saddle 整理已经存在的任务书、Git 版本、完成／审查记录；运行期间通过公开接口观察明确关联的任务和 agent，留存容易消失的最终回复和状态变化。严格区分原始记录、观测时间、推断和缺失，不收集完整会话。
3. 这条思路的风险尚未解决：JEV 原始返回仍可能捕获不到；TUI 关闭或轮询错过会丢信息；没有显式关联时，文件和 agent 归属可能不明。不能据此声称“只改 saddle 就能通用、可靠记录全部过程”。
4. 主控曾建议缺项标明／关联不明让用户确认，但用户只是要求新 Claude 再考虑，并未接受这些交互成本和完整性取舍。
5. 另一条可比较的轻量方向是按任务汇集现有证据、生成只读复盘档案，先证明复盘价值，再决定是否增加持续观察；这也不代表用户已放弃原始返回需求。

真实例子：T39 是两处展示修正，约定仅相关渲染检查，但实现者额外运行 workflow 并重复单个时序用例；主控认定超出预算。T40 有目标缺陷 RED→GREEN、复用现有组件和标准检查通过。相关任务记录在 docs/任务/。用户要能从过程材料发现这些差异，改进流程，而不是只看到最终 DONE。
