### 必须改

1. **必须改：重复选择正在接入的 B，会把随后输入交给仍连接着的 A。**
   - 位置：`src/terminals.rs:216–241`（`find` / `activate_existing`）、`src/app.rs:460–466`（去重后直接聚焦 Viewer）、`src/app.rs:919–944`（`focused_session`）。
   - 问题：`find` 将 `requested == B` 也当作已打开的 B。此时窗格中可能仍有未停止的 A session；`activate_existing` 返回 true，调用者直接切到 Viewer，而输入路径只检查 session 是否停止，没有检查它是否属于此次选择的 B。常见触发是慢 status 下再次按 Enter 或再次点击 B。
   - 复现：先接入 `p/a`；假 CLI 延迟 status；在 Agents 选择 `p/b` 并按 Enter；看到 `attaching p/b` 后再按 Enter，再输入 `Z`。探针实际记录 `input p/a 5a`，此时 B 的 status 尚未返回，未接入 B。断言 `typed Z after selecting pending B was delivered to old A` 失败。这是输入误路由，不只是提示文案问题。
   - 改法：区分“目标已有待处理请求”和“该目标已有可输入的 session”。待接入去重可以跳到原窗格，但不能因此把输入授权给旧 session；保持原生焦点或在正确目标接入前阻止终端输入。保留重选真正已连接的 A 时取消替换请求的现有行为，并补上述延迟 status 下重复选择 B 的回归。

2. **必须改：同一窗格改选 C 后，已过期但尚未创建 PTY 的 B 仍会接入。**
   - 位置：`src/terminals.rs:243–263`（`reserve`）、`src/terminals.rs:274–283`（`complete`）、`src/viewer.rs:24–36,88–121`（内部 pending / spawning）。
   - 问题：新的预留只更新外层 revision / requested，没有使 Viewer 内部的旧 pending / spawning 失效。B 的 status 一旦通过，B 就进入 Viewer.pending；若正在等待 A attach 退出，此时用户再选择 C，旧 B 仍会在 A 退出后启动。外层 Ticket 只能拒绝尚未消费的 status/start 结果，不能取消已经进入下一阶段的旧接入。
   - 复现：假 CLI 暂缓 A attach 的 SIGINT 退出；请求 B 并等到 A 开始退出（证明 B 的 status 已通过）；随后延迟 status 并改选 `p/c`，看到 `attaching p/c`；放行 A 退出。实际顺序为 `attach p/a → detaching p/a → detached p/a → attach p/b`，探针输出 `obsolete attach p/b = true`。之后放行 C，C 能正常接入，但过期 B 已被执行。断言 `B's obsolete pending PTY was still attached after the pane was reserved for C` 失败。
   - 改法：让替换操作同时使 Viewer 的旧待接入工作失效，例如将请求代次贯穿 status 到 PTY 接收阶段，或提供明确的取消待接入操作；已经创建的过期自有 attach 应回收且不能接收输入。无需改变“提交时预留目标”的裁决，也无需为取消 pending 而断开正常保留的现有 session。补“旧 attach 正在退出时再次替换”的回归。
