## 需求正文

目标：整理已有 UI 回归样例和运行入口，让公共样式调整后能及时发现排版退化，同时减少日常小改重复运行全量测试的成本。

一、整理现有样例
- 优先复用前几轮 UI 整理已经留下的宿主、Settings、Agents、Drover、Diff 等测试、合成数据和预览，说明主要界面的正常、空白、报错、长文本、窄窗口场景各由哪些现有样例覆盖。
- 提供明确、可重复的运行方式；沿用固定模拟数据和窗口尺寸，便于重复检查。复用现有测试工具和入口，不从零建立截图测试框架。
- 先确认覆盖缺口，再只补必要的样例或断言，避免同一行为重复测试；不铺开所有页面、主题、尺寸和设备的组合矩阵。布局正确性由检查验证，视觉观感仍需要人工查看。

二、写清分层运行约定
- 小改：运行直接相关检查。
- 公共样式或公共 UI 组件改动：运行相关 UI 回归组。
- 跨模块改动、阶段集成或发布前：运行全量检查。
- 将“什么改动需要运行哪些检查、对应入口是什么”写入清晰的开发约定；同步现有约定中需要调整的部分，避免 agent 每次小修都机械跑全套。保留有价值的现有测试，分别管理测试总量和每次运行范围，不靠删测试、放宽断言或超时来缩短耗时。
- 本任务的验证按实际修改范围选择：文档、运行入口和样例整理优先验证相应入口及受影响样例；需要全量时说明触发原因，不在每次小修后重复全量。

范围：这是轻量的样例整理与运行约定任务，不重做产品 UI，不新建庞大的测试平台，不搭车修复无关测试问题。考虑后续 T76 的 GPUI 评估，尽量保留可复用的合成数据，不把 Ratatui 绘制断言当成可直接迁移的 GPUI 测试，也不把完成全部 TUI 场景设为 GPUI 原型的硬门槛。
