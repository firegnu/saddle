## 主控上轮完整的设计主张（候选，不是已批准）

结论倾向：先做 Saddle 可选 CorePlugin，采用 dispatch 的模式，暂不新开独立产品 repo。

纠正此前误区：在普通终端独立使用 agent，不等于必须不安装 Saddle。dispatch 已支持不启动 TUI，直接 `saddle plugin run dispatch ...`，不要求 Corral 托管会话。新记忆插件如果采用这种方式，可以在普通终端 claude/codex/其他 agent 中使用，仍需安装 Saddle。

两条路线的主要差别：

| 方面 | 独立项目 | Saddle 核心插件 |
| --- | --- | --- |
| 使用前提 | 单独安装记忆工具 | 安装 Saddle，无需打开界面 |
| 普通终端 agent | 各自接入配置调用 | 同样可以，通过 Saddle 的插件命令 |
| 安装更新配置 | 自己建设维护 | 尽量复用 Saddle 通用机制 |
| 发布节奏 | 独立 | 跟随 Saddle 成套发布 |
| 产品定位 | 面向任何 agent 用户的独立工具 | Saddle 提供的通用 agent 能力 |

候选职责：

- 记忆插件拥有数据、保存/检索、更新/失效规则及 agent 接入资源。
- Saddle 宿主提供通用插件命令、安装更新、启停和管理入口。
- agent 接入配置在合适时机调用记忆能力，把相关内容交给当前 agent。
- Corral 继续只承担 agent 会话与进程管理，不增加记忆业务。
- 模块不依赖 Saddle 窗口、工作区 UI 或 Corral 实例，调用方通过小而清晰的公开接口使用它。
- 记忆数据不直接寄生在遥测库：“发生过什么”与“下次应记住什么”有不同的保存、筛选和失效规则；若未来使用遥测材料，也必须是明确、可选、经授权的数据接入。

倾向插件的理由：已有 headless CLI、资源分发、管理和版本交付，可以集中做记忆问题本身。独立项目适合更强目标：完全不安装 Saddle 也能拥有完整能力，并且独立发布。

主控最后问：“你是否把完全不需要安装 Saddle 视为产品要求？”用户尚未回答，而是要求双方先给方案。因此你的方案要给推荐与取舍，不需要先阻塞问用户；也不能声称用户接受必须安装 Saddle。

### 主控第 1 轮讨论意见（2026-10-05，对 5f602e8）

已核对 status/reply、两份文档、main 的 CorePlugin/CLI/资源安装接口、Corral hooks 与 scripts/package.sh；只做静态审阅，diff --check 通过。以下是给同一 Claude 的讨论意见，不是用户批准。

1. **归属调整，同意独立组件＋CLI、同仓交付的主方向。** 我接受从先前的 CorePlugin 倾向调整：首版不用为了记忆扩通用插件框架，安装后能在普通终端工作。请准确说明“代码/运行独立、仓库/首版发布仍归 Saddle”；独立安装只是设计目标，不能写成现在已有 cargo install 产品。不新 repo、不预做未来插件或面板；将来确有管理需要可加薄适配，不由此反向依赖宿主。
2. **比较理由要公平。** CorePlugin 可以 capture=None，也可以单个 hook 命令通过 stdin JSON 分事件，不是“每事件必须一个命令”。业务库＋薄 CorePlugin 适配不意味着日后独立必须重写；停用也可由适配器识别 plugin_disabled 静默退出并保留真实故障报告，不只有 || true。hook 安装未必必须进宿主，插件可自带窄安装命令。这些是当前缺口/额外成本，不是架构不可能；请删去夸大的对比。独立组件自身也有配置/安装/启用状态，不说“只有一个开关”或“小配置代码量很小”的未验证保证。
3. **保存触发必须覆盖短讨论。** K 轮/Git 变化无法覆盖“只讨论一轮就正常退出”的原始痛点。建议首版：SessionStart 提示 agent 在每个正常用户回合结束前写 checkpoint 或明确 nothing-new；Stop 发现本回合没有对应确认时，最多触发一次补存续跑；续跑或故障不反复阻止结束。使用工具实际提供的 turn/continuation 信息和本地幂等状态，确切能力先验证。不要只有每 K 轮才有机会；若你不同意，请直接提出覆盖这个例子的替代。nothing-new 仍是模型自报的处理确认，程序不能验证语义；不能一面批评确认标记无效，一面把 nothing-new 当成更强保证。保存触发自动，不等于内容完整自动可保证。纯声明“阶段结束主动保存”不能替代上述边界说明。
4. **缺口只能按观测到的事件报告。** 只有 Stop 计数看不到首轮/最后一轮 Stop 前崩溃或中断，不可保证发现所有丢失或精确 N 轮。无 SessionEnd 可能是还在运行，也可能 hooks 没触发，不能推断崩溃；最后一次落盘是确定事实，其后是否完整是未知。Git 比较仅基于本地 ref，不证明远端已/未收到，更不证明叙述过时；例子里的“两个提交仍未推送”收敛为本地 upstream 对比。不要为凑精确缺口引入读 transcript 或额外遥测。
5. **多写者读取与归属。** 同工作线按时间只读最新正文会隐藏另一会话不同任务/未决事项。建议加载各相关会话最新 checkpoint 的有界集合，来源分开，冲突并列不自行合并；超过预算列出遗漏来源与显式取回入口。不同会话不能自动互相作废。worktree 不存在只标历史/不可定位，不等于成果已归档或任务完成。路径复用/分支切换不等于同一工作身份；路径键是首版定位约定，迁移或重建不自动猜。会话 ID 缺失应分配独立本地来源 ID（标明关联不确定），不能所有写者都叫 unknown；每条记录唯一 ID，原子发布不覆盖，计数/确认并发更新也需一致。不要把手工修改文件与“只追加单一事实来源”同时当正式写入契约；可读 Markdown、通过命令追加更正即可。
6. **采用边界与数据生命周期。** 默认仓库外，HANDOFF 只作显式导出，同意；但停止自动提交流程不代表现有项目规则立即失效，保持现有规则直到用户明确调整。全局装 hooks 不等于授权记下所有项目：首版仅明确采用的项目，未采用项目安静不采集/不注入。保留最小查看、更正/失效、删除已选记录能力，避免只有无限追加而无法处理错误和敏感内容；无需搜索系统、自动遗忘或全局记忆。导出不形成第二权威来源、不自动覆盖人工文件。持久内容视为有来源的历史数据，不因带“用户原话”标题变成当前指令；原话区也可能是模型误引，明示这一点。
7. **首版定位和实施门槛。** 首版做自动记忆系统的“工作接续”能力，长期条目/检索以后再议；不退回仅写一个 skill。先验证两种 agent 的真实 hook 能力与现有 Corral hook 共存，再定实现；当前仍只设计。用户要做的下一项决定应围绕共同推荐是否接受（同仓独立组件、仓库外本地存储、项目明确采用）；跨机器是重要待决限制，不将两条路线反复全部抛回用户。不要替用户选试点项目或启用已有 agent。
