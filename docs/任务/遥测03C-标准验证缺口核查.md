### 2. 实际锁生命周期、隔离与子进程路径

- `src/plugins/registry.rs:230–270`：每次写入用新的 `std::fs::File` 打开 `plugins.lock`，申请 `LOCK_EX | LOCK_NB`；取得锁后才比较 baseline、写临时文件、sync/persist 并更新内存。局部 `lock` 在成功返回和 `ensure!`/`?` 的错误返回路径都会正常析构，没有保存到 `Registry`、显式 clone 或代码级泄漏；**但没有 `LOCK_UN`，释放依赖文件描述符关闭后的实际引用生命周期**。不能把“Rust 局部变量已 drop”直接等同于“内核已无其他引用”。
- `registry.rs:248–251` 对所有非零 `flock` 返回均给同一 busy 文案，没有读取 errno。因此真正锁竞争和其他系统错误在原日志中不可区分。busy 分支发生在 baseline/持久化之前；本轮未发现该失败路径覆盖他人 registry 或部分写入的证据。
- `tests/plugins.rs:59–94` 的两个 Registry 对象是同一临时路径上的顺序调用，测试名称中的 concurrent edit 是 stale snapshot 情景，并没有自己创建并发写线程。`first.add` 返回后、`stale.add` 报错后，正常 Rust 生命周期都已关闭各自局部锁；`stale.enabled` 失败不是两个长期存活的 Registry 对象本身长期持锁。
- `tests/core_plugins.rs:604–641` 使用单独 `Fixture::new()` 临时目录下的 `plugins.toml`；先明确手工加锁并检查写入报 busy，再于639行 `drop(lock)`，640行立即写入。这里不存在遗漏这条 drop 的源码事实，但 close 同样不证明继承引用已经消失。
- 两个失败测试及各自其他 fixture 都使用 `tempfile::tempdir()`；锁路径直接由各自临时目录构造，没有回落到共享 HOME/真实 registry。已核 tempfile 3.27.0 的 `tempdir_in → create_helper → DirBuilder::create`，目录名冲突不会复用既有目录。`core_plugins` 子进程的 HOME/config/state 和 TEST_* 路径由各自 fixture 设置；没有在父测试进程里全局 set/remove env。`plugin_driver` 的 dup2/exit 由子进程入口条件约束。**没有发现测试临时路径串用证据；路径隔离并不阻止同进程其他线程启动子进程时继承已打开的 fd。**
- `plugins` 同一测试二进制内有多个 `Runtime::start` 用例。`src/plugins/runtime.rs:325–349` 用 `Command::pre_exec(setsid)` 再 `spawn`；当前真实工具链 Rust 1.96.0（ac68faa20，aarch64-apple-darwin）的 `std/src/sys/process/unix/unix.rs:460–469,94,187–188` 表明存在 pre_exec closure 时放弃 posix_spawn，进入 fork 路径。若另一个线程正在 Registry 写入，fork 可复制那个锁 fd，子进程直到 exec/退出前仍可能持有它。此调用链真实存在，但原日志没有记录它与失败发生重叠。
- **`core_plugins` 必须单独看待**：其同进程子进程入口是 `Fixture::command` 的普通 `Command::new(current_exe())` 和真实二进制命令，无 pre_exec；失败测试自身的 Manager 使用空外部 registry、假 `test.core` Catalog，不启动 Runtime。按当前工具链源码及这些参数，普通命令可走 `posix_spawnp`。不能把 `plugins` 的显式 fork 链搬来当它的已证路径；本轮未探测 macOS posix_spawn 内部是否存在相关临时引用窗口。两者同文案不足以认定同根因。
- 已核当前 std `sys/fs/unix.rs:1359–1368`，Rust OpenOptions 原本就使用 `O_CLOEXEC`；**建议“补 CLOEXEC”不能解决此次实验中的 fork 到 exec 窗口**。SDK 自带 `flock(2)` 的 NOTES 说明 dup/fork 共享同一锁的引用；本轮另外用下面的实际实验核实该机制，没有仅凭文档作历史归因。

原始输出：

```text

```

这证明在本机即使设置 CLOEXEC，**父侧 close 之后仍可能因子进程的 exec 前继承引用而返回 EWOULDBLOCK；子进程完成后可立即取得锁**。屏障刻意固定了原代码中可能很短的窗口，未测故障发生频率；没有执行实际 `Registry::write`、两条原测试或普通 posix_spawn 场景。它验证的是原实现使用的锁释放机制，不是原失败的调度轨迹，也不是任何修复的 GREEN。
