# T49：自动记忆的产品边界与方案

**状态（第 2 轮修订，2026-10-05）**：主方向（同仓独立组件加 CLI 并随 Saddle 交付、仓库外本地存储、项目明确采用、每个正常回合都有保存机会）已经双方同意，属于"双方共同建议，待用户批准"。标了 **〔新增，待主控确认〕** 的条目是 Claude 本轮新提出的，主控还没审过，不算共识。

本轮仍然只做设计：没有实现、原型或测试，没有读本机私人会话或记忆文件。命令名（暂名 `mem`）、字段名、标记写法都是讨论用的草案。

第 1 轮初稿是 `5f602e8`；主控意见和 Claude 的逐条回应见[任务书](../任务/T49-自动记忆边界共识.md)的完成记录。

## 0. 结论

1. **归属**：做成独立组件。具体是一个 Rust crate 加一个 CLI，代码和运行都不依赖 Saddle 或 Corral。仓库和首版发布仍然归 Saddle：放在 Saddle 仓库，用 `scripts/package.sh` 和 Saddle 一起打包，这和 Corral 现在的做法相同（`scripts/package.sh:24-25`）。"不装 Saddle 也能单独安装"只是设计目标，靠"不依赖 Saddle crate"来保留这个可能，现在并没有可以单独安装的产品。不新开 repo；不提前做插件适配或界面。以后真有管理需要，可以加一层薄适配，但不能让记忆反过来依赖宿主。
2. **首版定位**：做自动记忆系统里的"工作接续"这一项能力。长期条目和检索以后再议，也不退回到只写一个技能。
3. **存储与采用**：
   - 记录存在仓库外、本机用户目录下，不进 Git，因此保存不需要提交或推送。
   - HANDOFF.md 只作为显式导出，不会变成第二份权威来源，也不会自动覆盖人写的文件。
   - hooks 全局安装后，只有用户明确采用的项目才会注入和保存，其他项目一律安静退出。
   - 现有项目规则（包括 Saddle 的 HANDOFF 规则）保持不变，直到用户明确调整。
4. **保存触发**：每个正常结束的用户回合都有一次保存机会。agent 在回合末尾要么给出接续记录，要么明确写"无新内容"。如果 Stop 时两者都没有，程序最多续跑一次让它补上，之后不再阻止结束。
   - "无新内容"只是模型自己报告"处理过了"，程序验证不了它说得对不对。
   - 触发是自动的，不代表记下的内容完整、准确。
5. **缺口只报告观测到的事实**：最后一次落盘是什么时候，以及之后观测到了哪些事件。之后发生了什么属于未知，不推断崩溃，也不说"丢了 N 轮"。
6. **多写者**：同一条工作线上，各个会话最新的记录有界地并列显示，来源分开，冲突也并列，不自动合并，也不按时间让新的覆盖旧的。
7. **历史与授权**：记录是带来源的历史数据，不是当前指令，也不是授权。记录里"用户原话"一栏也可能是模型引错了。
8. **按能力分档**：首版只接 Claude Code 和 Codex 的 hooks，不承诺所有 agent 都全自动。动手实现前，先实测真实的 hook 能力以及它和 Corral hooks 能否共存。

## 1. 用户要解决的问题

原话有两层：一是每个项目结束时都得提醒 handoff，然后提交、推送；二是新 session 还得让它先读 handoff。用户还说明，这个问题和 Saddle、Corral 都无关，在普通终端里单独用一个 agent 也会遇到。之后用户表示愿意做成自动记忆系统，现在要定边界。

由此得到的目标：在普通终端里用 Claude Code 或 Codex，不需要说"handoff"，也不需要说"读 handoff"。下一次开一个全新 session，哪怕换了工具，开局就能看到上次停在哪、有哪些可观测的现场变化、建议的下一步，而且不会把这些当成授权。哪怕只讨论了一轮就正常退出，那一轮也要有保存的机会。

## 2. 产品归属：公平比较

两条路都可行。下表比较的是各自的额外成本，不是"能不能做到"。

| 方面 | 薄 CorePlugin 适配 + 业务库 | 同仓独立组件 + CLI（共同建议） |
|---|---|---|
| 调用方式 | hooks 调 `saddle plugin run memory hook`；用一个命令、靠 stdin 里的 JSON 区分事件即可；可以不声明采集（`capture: None`） | hooks 直接调记忆 CLI |
| 第一次启用 | 现有设计只能在 TUI 里启用（[dispatch 设计 §6.4](../dispatch插件接口设计.md) 写明 v1 不提供 headless 启用）。要么接受"先打开一次界面"，要么重新决定是否加 headless 启用 | 记忆自己的 `install` 和 `adopt` 命令，在终端里完成 |
| 停用后 hooks 仍会触发 | 宿主在进入插件之前就以 125 拒绝（`src/plugins/cli.rs:152,223`），插件里的代码根本跑不到，所以"安静退出"做不进插件。要么在插件外加一层包装：读配对回执，`error.code=plugin_disabled` 时静默，其他错误照常报告；要么给宿主加一个选项 | 记忆自己区分"项目未采用 / 未安装"和"真故障" |
| 往 agent 配置里装 hooks | 插件可以自带一个窄的安装命令（参数走 stdin），不一定要扩宿主的资源安装器；现有安装器只管技能目录（`crates/core-plugin/src/lib.rs:27`、`src/plugins/resources.rs:31-36`） | 记忆自带安装命令；先 dry-run、征得确认，和 `corral install-skills` 的做法一致（`crates/corral-core/src/skills.rs:122`） |
| 自身要维护的状态 | 宿主里的启用状态，加上插件的安装状态和采用状态 | 安装状态、采用状态、配置，加上 Codex 那边的信任状态；不止一个开关 |
| 得到的好处 | Settings → Plugins 里现成的一行显示和接入说明；技能安装器（首版用不上） | 首次启用和停用两件事都不经过宿主；首版不改宿主；和 Corral"agent hooks 调稳定二进制"的结构相同（`crates/corral-core/src/hooks.rs:51` 以及 :86-122） |
| 以后能否独立 | 业务库本身可以独立，不必重写；适配层可以丢掉 | 原样就是独立的 |

**选独立组件的理由**：记忆的调用方是任意终端里的 agent hooks。CorePlugin 能复用的部分（目录、宿主启停、技能资源、受控采集）不是记忆最需要的。反过来，记忆需要的（在终端里启用、停用时安静、装 hooks）在 CorePlugin 路线下都要另外补。独立组件把这些补丁放在记忆自己里面，宿主不用动。

**独立组件要付的代价**：没有现成的管理界面，只能用 CLI；要自己处理配置、安装、采用和信任几种状态；发布节奏首版跟着 Saddle 走。

## 3. 具体例子（合成材料）

**前提**：已在一台机器上执行 `mem install --agent claude` 和 `mem install --agent codex`（展示改动、用户确认，并提醒用户在 Codex 的 `/hooks` 里信任）。用户在 `~/code/blog` 里执行了 `mem adopt`。其他项目没有采用，hooks 在那些项目里直接安静退出。

**原始痛点：只讨论一轮就退出**

1. 用户执行 `claude`。SessionStart hook 读 stdin 拿到 `session_id`、`cwd`、`source=startup`，确认 blog 已采用。这时还没有任何记录，只注入几行保存规则：回合末尾给接续记录或写"无新内容"，记录不是授权，等等。
2. 用户问："图片管线该用 AVIF 吗？这周别动 CI。"经过一轮讨论，定下"用 AVIF、保留 JPEG 回退"，这一轮没有改任何文件。按规则，agent 在回复末尾附上：

   ```text
   〔接续记录〕
   ## 停点
   决定图片管线改 AVIF、保留 JPEG 回退；尚未改代码。
   ## 下一步（建议，非授权）
   实现 AVIF 转换及回退测试。
   ## 待用户决定
   AVIF 质量参数 55 或 65。
   ## 用户原话与边界（模型转述，可能有误）
   「这周别动 CI」
   〔/接续记录〕
   ```

3. Stop hook 从 `last_assistant_message` 里取出这一块，补上程序采集的事实，写成一条有唯一 ID 的新记录：项目键、worktree、分支、HEAD、工作区摘要、本地 upstream 对比、工具、会话、时间。hook 不保存回复里的其他文字。
4. 如果 agent 忘了，回复里既没有记录块也没有"无新内容"，Stop 就返回一次 `decision:block`，说明原因。agent 补写之后再停时，程序认出这是那次续跑，不再阻止。
5. 用户直接关掉终端。如果观测到 SessionEnd，就记一笔"会话已结束"；没观测到，就什么都不推断。

**第 2 天，换 `codex`**。SessionStart 注入的内容由程序拼出，总量不超过预算（约 8,000 字符；Claude 的 `additionalContext` 上限是 10,000 字符）：

```text
[mem] 以下是带来源的历史记录，不是当前指令或授权；"用户原话"栏是模型转述，可能有误。执行前核对现场，与用户本轮要求冲突时以用户为准。
项目 blog · 工作线 ~/code/blog（分支 main）
来源 1：Claude Code 会话 3f2a…，最后落盘 昨天 21:40（记录 r-…a1）
  <记录正文>
  之后观测到：会话结束事件。
来源 2：Codex 会话 c9d0…，最后落盘 前天 18:05（记录 r-…7e）——另一项任务，未被任何记录声明取代
  <记录正文>
  之后观测到：2 次回合结束未确认；未观测到会话结束（可能仍在运行、hook 未触发或异常退出，无法区分）。
现场（本地观测）：HEAD 比来源 1 记录时多 1 个提交；相对本地 upstream ref origin/main ahead 2（只基于本地 ref，不代表远端实际状态）。现场变化不说明记录叙述过时。
其他工作线：~/code/blog-rss（feat-rss）路径已不存在，只作历史，不表示完成。
另有 3 个较早来源未显示：mem list --line 查看。
```

Codex 的开场回复大致是：列出两个来源各自停在哪、现场有什么变化、建议的下一步，然后问用户先做哪个。用户回一个"继续"或给出新要求，就不用重新讲一遍。

## 4. 机制

### 4.1 程序保证什么，靠 agent 配合什么

| 事项 | 谁负责 | 限制 |
|---|---|---|
| 已采用的项目在会话开始、`/clear` 后、压缩后注入记录 | 程序（SessionStart） | 需要装了 hooks 且工具确实执行；Codex 还需要信任。resume 时只补"之后的新记录和现场变化"，细节实测后定 |
| 每个正常结束的回合检查有没有确认，没有就最多续跑一次 | 程序（Stop 加本地状态） | 用户中断、崩溃、Stop 之前就退出的回合，没有这次机会 |
| 判断写不写、写什么，以及"无新内容" | 模型 | 程序验证不了语义；"无新内容"只是模型自报的处理确认 |
| 落盘、唯一 ID、原子发布、补上 Git 等事实 | 程序 | 叙述部分可能有误、不全，或者引错了话 |
| 现场对比 | 程序，在注入时现算 | 只基于本地 Git 和本地 ref；不 fetch；不证明远端状态，也不说明叙述过时 |
| 缺口报告 | 程序，只报观测到的事件 | 最后一次落盘之后的情况是未知 |
| 不把记录当授权 | 注入的声明加模型遵守 | 程序无法强制 |

### 4.2 保存触发

- **规则从哪来**：SessionStart 注入时就告诉 agent：每个正常回合的最后一条回复，结尾要么附 `〔接续记录〕…〔/接续记录〕`，要么附一行 `〔接续：无新内容〕`。
- **Stop 时怎么检查**：只在已采用的项目里检查，每次都看这一回合最后一条回复（`last_assistant_message`）：
  - 有完整的记录块：落盘，这一回合算已确认。
  - 有"无新内容"标记：只更新本会话状态，不产生记录。
  - 两者都没有，或者记录块不完整、超过长度上限：返回一次 `decision:block`，原因写明缺什么。
- **防止反复阻止**：本地状态记下"上一次 Stop 是我们阻止的"，下一次 Stop 就是那次续跑，不管结果如何都放行；续跑后仍然没有确认，只记一笔"观测到未确认"。Codex 另外有 `stop_hook_active` 可以用来核对。这次核对的 Claude 文档摘录里没找到对应字段，所以不依赖它。hook 自身出错或超时一律放行。
- **代价**：每个回合多一行可见标记；需要保存的回合，用户会在回复里看到记录块。好处是用户当场就能看到存了什么、引用的原话对不对，可以立刻更正。忘写时多一次模型续跑。这个代价是否可以接受，要在试用中看。

〔新增，待主控确认〕**写入路径**：首选"回复里的记录块，由 Stop hook 取出落盘"，`mem save`（正文走 stdin）作为备选，用于没有 hooks 的工具和手动保存。理由有三点：

- 每个回合都让 agent 调一次工具，在 Claude Code 里可能要逐次批准权限。
- Codex 在默认 workspace-write 沙箱下，可能不能写工作区以外的用户状态目录（这一点要实测）。
- hook 由工具自己执行，`session_id` 和 `cwd` 直接来自 hook 输入，会话关联更可靠。

hook 只从最后一条回复里取出标记块，不保存其他文字，也不读会话记录文件。如果实测发现两种工具里有一种拿不到 `last_assistant_message`，这个工具就改走 `mem save`，判断这一回合有没有保存时，以"上一次 Stop 之后有没有落盘"为准。

### 4.3 缺口报告

- **确定的事实**：每个来源最后一次落盘的时间和记录 ID。
- **之后观测到的事件**，按原样列出：
  - 回合结束时未确认的次数；
  - 有没有观测到会话结束；
  - 来源是不是只走 CLI、没有 hook 事件。
- **不推断**：没观测到会话结束，可能是还在运行，可能是 hook 没触发，也可能是异常退出，不区分。Stop 计数看不到在 Stop 之前就中断或崩溃的回合，所以不说精确丢了几轮，也不承诺能发现所有丢失。
- **不为此加采集**：不读会话记录，不加遥测，不调用模型。

### 4.4 多写者、身份与并发

- **加载哪些**：同一条工作线上，每个来源最新的、没有被撤回或被声明取代的记录，组成一个有界集合，各自标出来源。冲突的内容并列显示，不合并，也不按时间互相覆盖。超出预算的来源，列出数量和查看命令。
- **键是定位约定，不是身份**：
  - 项目键用采用时 Git 公共目录的路径；
  - 工作线键用 worktree 路径，分支只作为属性显示。
  - 路径被复用、分支被切换，都不等于"同一份工作"；仓库移动或重建后不自动猜测对应关系，需要重新采用。
  - worktree 路径不存在了，只标"已不可定位，只作历史"，不表示成果已经归档或任务已经完成。
- **来源 ID**：hook 路径用"工具 + 会话 ID"。CLI 路径如果拿不到会话 ID，就分配一个独立的本地来源 ID，并标明"会话关联不确定"，不会让所有写入者都叫 `unknown`。
- **〔新增，待主控确认〕显式取代**：不同会话之间不会自动互相作废。但如果完全不能取代，一条线上每个会话的最后记录都会永远在场。所以允许写入者在记录块里声明 `supersedes: <记录ID>`，只能列本回合确实接手的那些记录（注入时会给出各记录的 ID）。被声明取代的记录默认不显示，但会注明是谁声明的，可以查看，也可以用更正撤销这个声明。不声明就什么都不取代。
- **并发**：
  - 每条记录用唯一 ID 写成新文件，临时文件加 rename 原子发布，从不覆盖已有记录；
  - 每个会话有自己的状态文件，只有采用表需要加锁；
  - 同一会话的计数和确认状态在本会话 hook 里串行更新，并发写入者之间不共享可变状态。

### 4.5 采用与数据生命周期

- **采用**：`mem adopt` / `mem unadopt` 写在工具自己的状态目录里，不改仓库。未采用的项目不注入、不检查、不保存，也不提示。采用覆盖这个仓库的所有 worktree，包括被委派 agent 所在的 worktree（影响见 §7）。
- **查看、更正、删除**：
  - `mem list` / `mem show <ID>` 查看；
  - `mem correct <ID>` 追加一条更正记录，引用原记录；
  - `mem retract <ID>` 追加一条失效声明，原记录保留，默认不显示；
  - `mem delete <ID>` 物理删除正文，只留一个没有内容的墓碑，用于处理误存的敏感内容，这是"只追加"规则唯一的例外。
- **改动的写入契约**：Markdown 文件人可以直接读，但正式的改动一律通过命令追加，不把手工编辑当作写入方式。
- **导出**：`mem export` 输出到标准输出，或者写一个新文件。目标文件已存在时拒绝写入，不会覆盖人写的 HANDOFF.md。导出内容带"导出自 mem，时间…，非权威"的抬头。
- **不做**：搜索系统、自动遗忘、全局记忆。

### 4.6 数据格式

存放在 `$XDG_STATE_HOME/<名>/` 下，按项目键分目录：

- 记录：每条一个 Markdown 文件，前面是程序采集的元数据，后面是模型写的正文。正文用固定的小标题：停点 / 已完成及验证 / 下一步（建议） / 待用户决定 / 用户原话与边界（模型转述）/ 未落盘的讨论要点。程序只检查格式完整、长度不超上限（例如 4 KB），不检查语义。
- 会话状态：每个来源一个小 JSON 文件。
- 采用表：一个。

数据量小，所以首版不用 SQLite。

## 5. 接口草案

```text
mem hook <claude|codex>                    # 唯一的 hook 入口，按 stdin JSON 里的事件名分派
mem install|uninstall --agent <claude|codex> [--dry-run|--yes]
mem status [--json]
mem adopt | unadopt                        # 作用于当前目录所在的项目
mem show [--json]                          # 输出和注入相同的内容，给没有 hooks 的工具或人用
mem save [--source ID] [--nothing-new]     # 正文走 stdin；--nothing-new 只更新状态
mem list [--line] | show <ID> | correct <ID> | retract <ID> | delete <ID> | export [PATH]
```

- **hook 定义必须稳定**：Codex 要求用户审核并信任"这一份确切的 hook 定义"。所以命令要指向一个固定的绝对路径（可以学 Corral 的 `.runtime/helper` 软链接），升级时只换背后的二进制。
- **Claude 的 hook 写在哪**：用户 settings，还是官方插件的 `hooks/hooks.json`，实测后再定。
- **和 Corral 的关系**：不改 Corral，也不读 Corral 的事件文件。

## 6. 首版范围与非目标

**首版做**：
- 独立 crate 和 CLI，随 Saddle 一起打包；
- Claude Code 和 Codex 的 SessionStart、Stop、SessionEnd 三个 hook；
- 项目采用；
- 每回合确认，忘写时续跑一次补存；
- 仓库外存储；
- 多来源有界注入；
- 现场对比；
- 只报观测到的缺口；
- 查看、更正、撤回、删除、导出；
- install/uninstall/status。

**首版不做**：
- 长期条目、检索、自动遗忘、全局记忆；
- 读会话记录，或者为了补缺口另外调用 LLM、加遥测；
- 读 Corral 事件文件、读其他工具的记忆库；
- 自动提交、推送、fetch；
- 把记录当作授权；
- 跨机器同步；
- MCP；
- pi/omp 等其他 agent；
- Saddle 插件适配或界面；
- 改动宿主、插件框架或 Corral；
- 自动修改任何项目的规则或 HANDOFF。

## 7. 请用户决定

1. **是否接受共同建议**：
   - 同仓独立组件加 CLI，随 Saddle 交付；
   - 仓库外本地存储，HANDOFF 只作显式导出，现有项目规则不变；
   - 由你明确采用项目才生效；
   - 每个正常回合末尾有一行可见的确认标记，需要保存时会出现记录块，忘写时自动续跑一次。
2. **跨机器**：首版只在本机生效。在另一台机器上没有记录，这是一个重要的待决限制。如果你需要跨机器接续，请说明，我们再设计同步方式（指定同步目录，或者导出到 Git）。

试点项目在实现完成后由你执行 `mem adopt` 自己选，我们不预先替你选，也不启用任何现有 agent。还有一点需要知道：如果你采用了用 Saddle 主控分派的项目，被委派 agent 的会话也会每回合确认；这部分成本在试用中观察，不提前设计排除规则。

## 8. 逐步验证

1. **先实测 hooks，再定实现**：用隔离的 HOME 和合成项目，开自己的 `saddle/test-*` agent 或一次性会话，逐项确认：
   - 两种工具的 SessionStart 在各种来源下能否注入；
   - Stop 能否拿到 `last_assistant_message`；
   - Stop 返回 `decision:block` 后是否续跑，续跑能否被识别、只阻止一次；
   - 用户中断时 Stop 会不会触发；
   - hook 出错是否会放行；
   - SessionEnd 在时限内能否落盘；
   - Claude 调 `mem save` 是否需要批准权限，Codex 在默认沙箱下能否写用户状态目录；
   - hook 文本不变时，升级二进制后 Codex 的信任是否保留；
   - 用户级 hooks 和 Corral 通过 `--settings`、`-c` 注入的 hooks 是否叠加执行。

   这些结论决定写入路径和"自动"二字的边界。只要有一项不成立，就回来修改方案。
2. **存储、渲染和状态的单元测试**（临时目录、合成 Git 仓库）：唯一 ID 加原子发布、多来源有界选择、显式取代、更正/撤回/删除、现场对比用语、缺口用语、不推断、并发写入。
3. **hook 适配与安装**：用固定的 hook JSON 夹具测试；在隔离 HOME 下 dry-run，保留已有的用户 hooks；未采用的项目安静退出。
4. **用户试点**：由用户自己采用试点项目，观察是否还需要提醒 handoff 或"读 handoff"、标记带来的负担、续跑频率、有没有把旧记录当成现状。结束后再决定是否调整 Saddle 自己的 HANDOFF 规则。

## 9. 讨论记录摘要

第 1 轮里分歧较大的几点和处理结果（逐条回应见任务书）：

- **归属**：主控接受从 CorePlugin 改为同仓独立组件；Claude 修正了上一轮比较中夸大的部分（§2）。
- **保存触发**：初稿的"K 轮或 Git 变化"覆盖不到只讨论一轮就退出的情况，已改成每个回合确认；也收回了"保存本身比确认标记更可靠"的说法，两者都只是模型自报。
- **缺口、多写者、采用和生命周期**：按主控意见改正；另外新增显式取代和写入路径两条，待主控确认。
