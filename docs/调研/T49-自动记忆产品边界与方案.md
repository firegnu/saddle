# T49：自动记忆的产品边界与方案

**Claude 首轮建议，待主控讨论。** 2026-10-05，基于 `df1c727`。这不是双方共识，也不是用户批准；没有写实现、原型或测试，没有读本机私人会话或记忆文件。文中命令名、字段名、阈值都是讨论用草案。

## 0. 结论

1. **归属：建议做成独立组件，不做 CorePlugin。** 记忆核心是独立 Rust crate，加一个独立 CLI（暂名 `mem`，名字待定），不依赖任何 Saddle crate。首版放在 Saddle 仓库、随 Saddle 安装包一起发布，和 Corral 现在的做法一样（`crates/corral-core` 加独立 `corral` CLI，`scripts/package.sh:24-25` 把两个二进制并排打包）。Saddle 以后需要显示记忆时，只调用它的公开 CLI。要不要拆成单独 repo，等用户决定要不要给别人用、要不要独立发版时再定；因为没有依赖，拆起来不难。
2. **首版只做"会话接续"，不做通用长期记忆。** 记录的是"这条工作线停在哪、下一步是什么、哪些事待用户决定、哪些讨论还没落盘"。偏好和长期规则继续放在项目指令文件和各工具自带的记忆里。检索、语义搜索、自动摘要会话记录都不进首版。
3. **记录默认存在仓库外**（用户状态目录），不进 Git。保存就不用再提交、推送，从根上去掉"handoff → 提交 → 推送"这条链。想把记录留在仓库里的项目，可以导出成 HANDOFF.md。跨机器接续是否需要，交给用户决定（§7）。
4. **内容由模型判断，执行由程序完成。** 程序负责：在会话开始时注入记录；检测到"该存了"的信号时请 agent 保存，但会限频；存储；当时的 Git 事实由程序采集；对比现场算出哪些已经过时；检测最近一次保存之后、会话结束之前没存下来的那一段。agent 负责写叙述部分。记录只是历史，不构成执行授权。
5. **自动程度按工具能力分档**，不承诺所有 agent 都全自动。首版只接 Claude Code 和 Codex 的 hooks；其他工具靠项目指令里的一行说明，或者手动跑 `mem show`。

## 1. 用户要解决的问题与边界

痛点（原话）有两处：每个项目结束时都要提示 handoff，然后提交、推送；新 session 还要让它先读 handoff。用户随后说明，这和 Saddle、Corral 都无关，在普通终端里单独用一个 agent 也会遇到。后来又表示愿意把它做成自动记忆系统，目前在定边界。

据此，成功标准是：在普通终端里用 Claude Code 或 Codex 工作，不需要说"handoff"，也不需要说"读 handoff"。下一次全新 session，包括换成另一个工具，开局就能看到上次的停点、现场有什么变化、建议的下一步，并且不会把旧记录当成授权。

全新 session 需要会话之外的记录，这一点主控已经承认：代码和 Git 还原不出没落盘的讨论和授权。所以问题不在于要不要记录，而在于谁来触发、谁来写、存在哪、谁来读。

## 2. 产品归属：三条路的实质差别

主控对比了"独立项目"和"CorePlugin（dispatch 模式）"两条路。我加第三条：**仓库内独立组件（Corral 模式）**。这不是为了凑数：仓库里已经有这个先例，而且它正好对上记忆要解决的那几处不匹配。

| 判断依据 | 记忆的实际需要 | CorePlugin（dispatch 模式） | 独立组件（Corral 模式，推荐） |
|---|---|---|---|
| 谁来调用 | 任意终端里 agent 的 hooks，每个会话、每轮都会触发 | 原本为主控按技能调用设计 | Corral 的 `__hook` 帮助程序就是"agent hooks 调一个稳定的二进制"（`crates/corral-core/src/hooks.rs:51` 起的 helper，以及 :86-122 的注入） |
| 启用开关 | 装上 hooks 就该生效，不该再依赖界面 | 启用只能在 TUI 里做（[dispatch 设计 §6.4](../dispatch插件接口设计.md) "v1 不提供 headless enable"）。停用时 `run` 返回 125（`src/plugins/cli.rs:152,223`），hooks 照样触发，Claude Code 每次会话里都会出现 `<hook name> hook error`（官方 hooks 文档：非 0、非 2 且没有 JSON 时会提示）。结果是两个开关，外加一种噪音状态 | 只有一个开关：hooks 装没装，加上配置里的 `enabled` |
| 要装进 agent 的东西 | 往 `~/.claude/settings.json`（或 Claude 插件）和 `~/.codex/hooks.json` 写 hook 定义，这些是用户共用的文件 | 资源安装器只支持 `AgentSkill`（`crates/core-plugin/src/lib.rs:27`），目标固定为 `~/.claude/skills`、`~/.agents/skills`（`src/plugins/resources.rs:31-36,422`），按"整个目录归自己"管理所有权，不能合并进共用文件。要做就得在宿主新增一种"合并共用配置文件"的资源，而用到它的只有记忆一家 | 记忆自己带一个窄范围的 `install`/`uninstall`，先 dry-run、征得确认，和 `corral install-skills` 的做法一致（`crates/corral-core/src/skills.rs:122`） |
| CorePlugin 独有的好处 | 记忆用不上采集 Recorder 和起止回执；hooks 只需要干净的 stdout | Recorder、遥测回执、技能安装、管理页一行 | 不需要这些。保存规则由 hook 输出直接带给 agent，首版不装技能 |
| 不装 Saddle 能不能用 | 主控问过用户是否硬性要求，用户还没答 | 如果答"是"，就得重写 | 两种答案都成立：随 Saddle 打包，也能单独 `cargo install` |
| 依赖方向 | 记忆不能依赖 Saddle 或 Corral | 插件只依赖 `saddle-core-plugin`，满足 | 零依赖；Saddle 用公开 CLI 消费 |

独立组件的代价，如实列出：
- 失去 Settings → Plugins 里现成的一行管理和接入说明。首版用 `mem status`/`install`/`uninstall` 代替；以后 Saddle 想显示，再读 `mem status --json`。
- 要自己写参数解析和一个小配置文件，代码量很小。
- hook 安装代码两条路都得写，只是放的位置不同。

所以分歧的本质是：记忆是"被 agent hooks 调用的底层能力"，还是"Saddle 提供的业务命令"。我认为是前者。dispatch 用得上 CorePlugin 的那部分（受控采集、主控按回执判断），记忆都用不上。记忆真正需要的那部分（headless 启用、往共用配置里装 hooks），CorePlugin 又没有。

如果最终选 CorePlugin，宿主至少要补三项：hook 配置资源类型（合并共用文件，并且能区分哪些条目归自己）；headless 启用，或者接受"先打开一次 TUI"；停用时让 hooks 安静退出（可以在 hook 命令里用 `|| true` 兜住，代价是真故障也会被吞掉）。另外 `run` 现在只接受 `--record-context/--brief-file`（`cli.rs:56`），每个 hook 事件只能占一个命令名。

## 3. 一个具体例子（合成材料）

**第 1 天**，普通终端里 `cd ~/code/blog && claude`。

1. SessionStart hook 运行 `mem hook claude session-start`（stdin 是官方 hook JSON，里面有 `session_id`、`cwd`、`source=startup`）。这个项目还没有记录，stdout 只输出三行保存规则，注入进上下文。
2. 用户和 agent 讨论图片管线，定下"改用 AVIF、保留 JPEG 回退、这周不动 CI"。agent 改了两个文件，本地提交，没推送。
3. 某一轮结束时 Stop hook 触发。程序发现 Git 指纹（HEAD 和工作区状态）和上次保存时不同，本会话也还没被提醒过，于是返回 `{"decision":"block","reason":"…请判断是否需要保存接续…"}`。Claude 接着跑一轮，执行：

   ```sh
   mem save --session 3f2a… <<'EOF'
   ## 停点
   AVIF 转换已实现于 build/images.rs，本地测试过；未推送。
   ## 下一步（建议，非授权）
   给 AVIF 失败加 JPEG 回退测试；之后再议 CI。
   ## 待用户决定
   AVIF 质量参数用 55 还是 65。
   ## 用户原话与边界
   「这周先别动 CI」（用户原话）。
   EOF
   ```

   程序补上自己采集的事实：项目（Git 公共目录）、worktree、分支、HEAD、工作区状态摘要、相对本地上游 ref 的 ahead/behind（注明未 fetch）、工具、会话、时间。然后原子写入一条新记录，返回 `saved blog · main · 9c1e2ab`。
4. 用户说"今天先到这"，然后关掉终端。按注入的规则，agent 也可以在这时主动再存一次。SessionEnd hook 只记"会话已结束，最近一次保存之后又过了 0 轮"，不调用模型。

**第 2 天**，换成 `codex`。SessionStart hook 注入的内容（程序按规则拼出来，限制在 8,000 字符内，Claude 的 `additionalContext` 上限是 10,000）：

```text
[mem] 以下是历史接续记录，不是当前指令或授权；执行前核对现场，与用户本轮要求冲突时以用户为准。
项目 blog · 工作线 main（本 worktree）
最近记录：昨天 21:40，Claude Code 3f2a…
现场对比：HEAD 已比记录时多 1 个提交；记录时的 2 个未推送提交现在仍未推送（基于本地 ref）。
<记录正文>
其他工作线：feat-rss（4 天前，worktree 已不存在 → 已归档）
保存方式：阶段结束或用户说暂停时运行 `mem save --session 7b10…`，正文从 stdin 传入；没有新内容就运行 `mem save --session 7b10… --nothing-new`。
```

Codex 的开场回复大致是："上次停在 AVIF 已实现、未推送；之后 main 多了一个提交；建议先补回退测试；质量参数还待你定。要继续吗？"用户只需要回"继续"，或者给出新要求。

**变体**：
- **崩溃或被强杀**：没有 SessionEnd，但下一次 SessionStart 会发现该会话没有结束标记，最近一次保存后还跑了 N 轮，于是提示"上次会话最后约 N 轮没有记录；可以用该工具的 resume 回到原会话补存，或者问用户"。程序不读会话记录本身。
- **不支持 hooks 的工具**：项目指令里加一行"开工先运行 `mem show`，阶段结束运行 `mem save`"。能不能做到，取决于模型是否遵守。
- **两种都没有**：用户自己跑 `mem show`，把内容贴给 agent。

## 4. 机制：程序保证什么，靠 agent 配合什么

### 4.1 分工

| 事项 | 谁来做 | 前提或限制 |
|---|---|---|
| 新会话、`/clear` 后、压缩后注入记录 | 程序（SessionStart；压缩后会再注入一次；resume 时只补"这之后其他会话的新记录和现场变化"，具体试用时定） | 已装 hooks，且工具确实执行了；Codex 还需要用户在 `/hooks` 里信任 |
| 现场对比（是否有新提交、是否推送、worktree 是否还在、是否有未提交改动） | 程序，在注入时现算 | 只基于本地 Git，不 fetch，结果会注明 |
| 判断"该不该提醒保存" | 程序：看确定性信号并限频（§4.2） | 只能判断"大概有变化"，判断不了"值不值得记" |
| 判断"值不值得记、写什么" | 模型 | 内容可能不全或有误，程序不验证叙述 |
| 存储：原子写入、不同会话互不覆盖、Git 事实由程序填 | 程序 | agent 只通过 `mem save` 写，不直接改存储文件；人可以手工编辑 |
| 发现最近一次保存后没存下来的一段 | 程序（SessionEnd 记结束标记；没有标记就视为状态未知） | 缺的那段内容找不回来，只能提示 |
| 不把记录当授权 | 注入的文字声明；模型遵守 | 程序没法强制 |

### 4.2 保存触发：用"保存本身"作为完成标记，并限频提醒

对主控"保存检查完成标记"的评估：如果额外设一个"这一轮考虑过保存"的标记，agent 只要写一下标记就算过关，程序验证不了它到底考虑没有，等于多了一个没有意义的状态。我的建议是不设单独的标记，**直接把每次保存（包括 `--nothing-new` 这种确认）当作那个标记**：

- 程序给每个会话记三样东西：最近一次保存时的 Git 指纹、轮数、时间。每次 Stop 都更新轮数。
- 什么时候算"有变化"：Git 指纹和最近一次保存时不同；或者距离最近一次保存已经有 K 轮（纯讨论不改代码时，靠这一条兜底）。
- 限频：每 M 轮最多提醒一次；本轮如果就是由提醒引起的续跑，就不再提醒。这个防循环状态由程序自己保存，不依赖工具传入的字段（Codex 文档有 `stop_hook_active`，Claude 这次核对的文档摘录里没有找到这个字段，所以不依赖它）。
- agent 收到提醒后，要么 `mem save`，要么 `mem save --nothing-new`，两者都会把计数清零。如果它什么都不做，下一个时间窗口还会再提醒，不会无限阻止停止。
- K、M 的取值要在试用中调；被委派的 agent 提醒是否过多也要在试用中观察（§7 问题 3）。

**做不到的事要说清楚**：Stop 是"一轮回复结束"，不是"进程退出"。SessionEnd 时模型已经没有机会动作，而且时间很短：Claude 默认共享 1.5 秒（可调到最长 60 秒），Codex 默认 1 秒、最长 3 秒。所以这里只记结束标记，不做摘要。用户中断、崩溃、硬杀时，最近一次保存之后的内容会丢，首版只能如实提示。用另一个 LLM 在会话结束后读会话记录做摘要，不进首版（§6）。

### 4.3 归属与并发

- **项目**：用 Git 公共目录的规范路径作为键，同一个仓库的所有 worktree 共用（这和 Claude 自动记忆"按仓库、各 worktree 共享"的口径一致）。不在 Git 里的目录用当前目录作为键。
- **工作线**：worktree 路径加分支。注入时先给本工作线的完整正文，其他工作线每条一行；worktree 已经不存在的标记为已归档。
- **会话**：工具名加会话 ID。会话 ID 由 SessionStart 注入的保存命令带过去，agent 原样照抄；缺了就记 `unknown`。
- **写入只追加**：每次保存都是一个新文件（时间、工具、会话），用临时文件加 rename 写入；只有会话计数文件需要加锁。不存在"多个会话共同覆盖一份项目摘要"的情况。同一条工作线上两个并行会话都写了，注入时显示最新那条，并注明另一个会话几分钟前也写过。
- **跨项目**：互不加载。首版没有用户级的全局记忆。
- **Saddle 的分派方式**：主控在主 checkout 那条线；被委派的 agent 各自在自己的 worktree 线上写，对主控只显示为一行。任务文件仍然是交付的权威依据。这些记录也不会进入遥测库。

### 4.4 数据格式

放在 `$XDG_STATE_HOME/<名>/projects/<项目键>/` 下，每条记录一个 Markdown 文件，前面是程序采集的元数据（TOML 或 JSON），后面是 agent 写的正文。正文用固定小标题：停点 / 已完成及验证 / 下一步（建议） / 待用户决定 / 用户原话与边界 / 未落盘的讨论要点。程序只检查正文非空、长度不超过上限（例如 4 KB），不检查语义。选文件而不选 SQLite，是因为每个项目的数据量很小，人能直接读、改、grep，工具坏了数据也还在。以后真需要检索，再在旁边加索引。

## 5. 接口草案（首版）

```text
mem hook <claude|codex> <session-start|stop|session-end>   # hook 入口，stdin 是官方 hook JSON
mem save [--session ID] [--nothing-new]                     # 正文从 stdin 传入；按当前目录确定项目和工作线
mem show [--json]                                           # 输出和 SessionStart 注入相同的内容，给没有 hooks 的工具或人用
mem install --agent <claude|codex> [--dry-run|--yes]        # 写入 hook 定义；先展示改动、需要确认、改前备份
mem uninstall --agent … / mem status [--json]
```

- **hook 定义必须保持不变**：Codex 要求用户审核并信任"这一份确切的 hook 定义"。所以命令要指向一个固定的绝对路径（可以学 Corral 的 `.runtime/helper` 软链接），升级时换的是背后的二进制，hook 文本不动，不然每次升级都得重新信任。
- **Claude 的 hook 写在哪**：可以写用户 settings（共用文件，要合并、备份），也可以做成官方 Claude Code 插件的 `hooks/hooks.json`（所有权更干净，但需要用户在 `/plugin` 里操作一步）。先实测再选（§8 第 1 步）。Codex 优先用独立的 `~/.codex/hooks.json`。
- **和 Corral 的关系**：Corral 托管的 agent 启动时通过 `--settings` 或 `-c` 注入自己的 hooks，和用户级 hooks 并存（是否真的叠加执行要实测）。不改 Corral，也不读 Corral 的事件文件：里面虽然有 prompt 和最后一条回复，但那是 Corral 的内部数据。

## 6. 首版范围与非目标

**首版要做**：独立 crate 和 CLI；Claude Code 与 Codex 的 SessionStart、Stop、SessionEnd 三个 hook；仓库外按项目和工作线存储；注入、现场对比、找出缺口；限频提醒；install/uninstall/status；可选导出 HANDOFF.md；打进 Saddle 安装包。

**首版不做**：
- 通用长期记忆、偏好学习、检索或向量搜索、记忆过期策略（只按"新记录取代旧记录"和"worktree 消失就归档"）。
- 读会话记录、调用 LLM 自动摘要、读其他工具的记忆库或 Corral 的事件文件。
- 自动提交或推送、自动 fetch 或 pull；把记录当作执行授权；接遥测。
- MCP 服务、pi/omp 等其他 agent、跨机器同步、Saddle 界面。
- 改动 Saddle 宿主或插件框架、Corral；自动修改任何项目的 AGENTS 或 HANDOFF 规则。

**以后可能长成的样子**（不承诺）：带类型、显式置顶的长期条目；纯文本 `mem search`；同步目录；Saddle 只读面板。每一项都单独评估，不预留扩展点。

## 7. 真正需要用户决定的问题

1. **归属**：采用独立组件（本文推荐），还是 CorePlugin（主控上一轮的倾向）？另一个相关问题：以后是否打算给别人用、或者要求完全不装 Saddle 也能用？这决定什么时候拆成单独 repo，但不影响现在这样做。
2. **存放位置**：记录默认存在仓库外（推荐，省掉提交和推送），还是存在仓库里的 HANDOFF.md？你是否需要在另一台机器上接着做？如果需要，是指定一个同步目录，还是导出到 Git。
3. **试用范围**：先在哪 1–2 个项目试？被委派的 agent（`saddle/dev-*`）也启用，还是只在主控和普通会话里用？Saddle 本项目 AGENTS 里"收尾后更新 HANDOFF"这条规则先不动，试用后再决定。

## 8. 逐步验证建议

1. **先验证 hooks，再写存储**：用隔离的 HOME、合成项目，开自己的 `saddle/test-*` agent（或一次性会话），验证以下几点：SessionStart 在 startup、clear、compact、resume 四种情况下是否注入；两个工具的 Stop `decision:block` 是否会续跑，自己的防循环是否生效；SessionEnd 正常退出时能否在时限内落盘；hook 文本不变时，升级二进制后 Codex 的信任是否保留；用户级 hooks 和 Corral 注入的 hooks 是否叠加执行。这些结果是"自动"二字的依据，有任何一项不成立都要回来改方案。
2. 存储与渲染用单元测试覆盖（临时目录、合成 Git 仓库）：只追加、项目和工作线的键、现场对比、字符预算截断、缺口检测、两个会话并发保存。
3. hook 适配与 install/uninstall：用固定的 hook JSON 夹具，在隔离 HOME 下 dry-run，保留已有的用户 hooks。
4. 用户在选定项目上试用约一周，观察：还需不需要说 handoff 或"读 handoff"；提醒频率；有没有把过时记录当成现状；缺口多不多。然后再讨论 Saddle 本项目的 HANDOFF 规则。

## 9. 与主控上一轮主张的异同

**同意**：
- 记忆业务不进 Corral。
- 不依附遥测库，以后如果要用遥测材料，也必须明确授权、可选接入。
- 模块不依赖 Saddle 窗口、工作区或 Corral 实例，只通过公开接口使用。
- 保存与提交、推送分开，不会因为保存而推送。
- 并行会话不覆盖同一份摘要。
- 按工具能力分档，不承诺所有 agent 都全自动。
- 本轮不新开 repo。
- "在普通终端单用一个 agent 不等于不能装 Saddle"这一纠正本身是对的。

**不同意或需要修正**：
1. **CorePlugin 作为载体**（§2）：启用只能在 TUI 里做；装 hooks 需要共用配置文件资源，宿主还没有；CorePlugin 独有的采集和回执又用不上。所以"无需打开界面"在启用这一步并不成立。建议改成 Corral 模式的独立组件。
2. **"每项目短 HANDOFF"作为存储**：如果指的是仓库里的 HANDOFF.md，那它保留了用户要去掉的提交、推送那一步；而且分支和 worktree 各有一份，主仓库近期也有多条"交接"提交。建议默认存在仓库外，HANDOFF.md 只作为可选导出。
3. **"保存检查完成标记"**：理由见 §4.2。建议用保存本身作为标记，加确定性的触发信号和限频，不另设"考虑过"标记。
4. **用"通用交接技能"承载保存规则**：对有 hooks 的工具，SessionStart 注入和 Stop 提醒本身就带着规则，首版不需要装技能；没有 hooks 的工具用一行项目指令就够了。省掉一种需要安装的资源。
5. **SessionStart 注入**这一点同意，但需要补三项：程序现算的现场对比、"不是授权"的开头声明、压缩后再注入一次。
