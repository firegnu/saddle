## 1. 结论先行

用户进一步明确：这是一个产品，不能继续由三四个独立包、不同语言的工具拼装。最终对用户只有 Saddle 的安装、版本、升级和运行入口。

**迁移顺序确定为由外向内：先实现 Rust 的 Saddle 核心遥测与 corral-dispatch core plugin，整理掉外围的独立脚本/安装/调用依赖，最后迁移真正的 infra Corral。** 此决定替代本报告首轮“优先移植 Corral、dlog 暂作外部可选集成”的建议。

- corral-dispatch 纳入官方插件；dispatch-log 的能力由 Saddle 核心重做，保存更完整的需求、任务书版本与执行链路。旧日志不导入。
- core plugins 指产品自带、共同构建测试和发布的功能模块。内部仍有清晰接口，用户无需分别安装、配置路径或协调版本；是否单独启停、具体运行方式待设计。
- 先完成记录能力与派发工具的 Rust 化、skill 随产品提供，以及 Saddle/Drover 的接入；这期间 Corral 保持现有公开契约和运行实现。
- 外层收敛到一个明确的 agent 操作接口后，再替换 Corral 核心。不得把任务编排、记录业务下沉到 Corral，也不得让上层读它的内部文件。
- 统一产品不要求把全部功能放进同一个进程。可以保留进程隔离；但官方功能必须由 Saddle 统一提供，不把内部模块变成用户需要管理的多个包。
- Rust 化针对可执行工具逻辑；skill 的 Markdown 指令仍是版本化资源，不应机械翻译成刚性的流程代码。外部 Claude Code/Codex/pi/omp 仍是被托管工具。

以下源码事实仍有效；迁移步骤已按用户最新决定重排。示意目录、命令和运行方式尚未实施。

## 3. 目前到底有几层

```text
主控 agent
  ├─ 读取 corral / corral-dispatch skills
  ├─ 可选调用 route.py（TypeSafe 网络建议）
  └─ 调用 corral；项目流程另用 dlog 保存派发记录

Saddle TUI
  ├─ corral ls/status/... 子进程 → Corral 公共 CLI
  ├─ viewer PTY → corral attach → agent 独立 pen → agent PTY → 外部 agent
  ├─ 本实例 saddle ctl socket
  └─ 进程插件：Drover / Diff / demos
       └─ Drover 调用 Corral；Dispatch 视图按需调用 dlog
```

### Corral 是机制，不是任务调度器

Corral 是 Python 3.11+、仅标准库的程序。每个 agent 有独立 pen 进程，负责 PTY、socket、输入输出、状态事件和退出过程；不存在统一托管全部 agent 的中央 daemon。

这已经实现“关闭 Saddle，agent 继续运行”。此外 `send --after` 会脱离启动临时等待进程；统一发布不能漏掉这个后台角色，更不能把 `pending: true` 误当投递成功。参见 Corral `spawn.py:177`、`cli.py:214`、`pen.py`。

核心接口不止 start/stop：还有 send/keys/status/wait/reply/where/ls/read/attach，以及 instance 身份、错误码、输入来源、人类输入保护、旧 pen 协议兼容。`docs/CONTRACT.md` 明确公共契约是 CLI、JSON 和退出码，内部状态文件不是上层接口。

### corral-dispatch 是指令与少量工具

README 明确它不被 Corral 程序引用。SKILL.md 描述主控拆任务、模型选择、worktree、审查、合并和收尾；route.py 请求分类建议，失败时主控仍可判断。它没有一个需要“搬进去”的常驻调度服务。

本机技能目录通过软链接指向 Corral 源码目录，合仓移动目录后必须处理链接，否则旧 skill/route.py 会失效。将技能随版本打包，可以避免日常运行依赖开发 checkout；但安装到用户/项目技能目录仍应是明确动作，不能启动一次就静默覆盖用户规则。

### Saddle 目前仍依赖外部 Corral 可执行文件

`src/main.rs` 只分流 `ctl` 和 TUI/config。`src/corral.rs` 用配置里的程序名创建子进程；`src/viewer.rs:194` 创建 `[corral, attach, name]`。现有 `corral` 配置是**一个程序路径**，不是命令字符串，不能简单改成 `"saddle agent"` 就完事。

当前 viewer 的 PTY 与 Corral 的 agent PTY 是两层不同职责：前者显示 attach 客户端，后者真正托管 agent。合仓不必顺便移除这层或改终端渲染；先让现有 attach 路径换成统一入口即可降低迁移变量。

### 现有插件宿主不是无界面的运行核心

清单支持相对 executable、args、能力声明和视图。协议已有 `command.v1`、panel、notify、attention、view context 等能力，但没有 skill 安装贡献机制，也没有独立于 TUI 的通用插件 daemon。

插件 runtime 由 Saddle 实例持有，drop 时停止；`saddle ctl plugin` 需要运行中的宿主和插件。Drover 随 Saddle 退出停止观察和通知是用户已经接受的行为（`docs/DESIGN.md:1150` 起）。把 Corral直接套进这个生命周期，会使“退出界面后 agent 继续运行”丢失或需要特殊逃逸。

因此 Corral 应是能够脱离界面使用的运行核心。Drover 和 dispatch 工作流不应反向成为核心启动前提。

## 4. 从 Herdr 该学什么

Herdr 的重点不是“同一进程做完所有事”，而是一个安装入口覆盖多个运行角色。官方说明界面可以断开，后台 server 保留终端；server/机器重启后的恢复不等于原进程还活着。[官方概览](https://github.com/herdrdev/herdr)、[会话恢复说明](https://herdr.dev/docs/session-state/)。

固定版本源码中 `src/main.rs:445` 将 skill 编入二进制；`main.rs:560` 分流 server 模式；`src/server/autodetect.rs:194` 使用当前可执行文件启动后台 server。可借鉴统一版本、统一入口、随版本附带技能的做法。[v0.9.3 main](https://github.com/herdrdev/herdr/blob/v0.9.3/src/main.rs)、[server 启动](https://github.com/herdrdev/herdr/blob/v0.9.3/src/server/autodetect.rs)。

其插件通过公开 CLI/socket 调用宿主，宿主提供 `HERDR_BIN_PATH`，避免插件猜 PATH 或仓库位置；工作流留在插件，终端/agent 机制留在核心。Saddle 可借鉴这个安装位置发现机制，不需要替换已经实现的结构化面板协议。[官方插件说明](https://herdr.dev/docs/plugins/)。

不建议此次照搬中央 server、远端接入、热移交、marketplace 或改终端引擎。它们不是单一安装入口的必要条件。Herdr 源码构建还涉及 Rust、Zig/终端库；它能提供简单用户安装，不代表源码构建也只有一层依赖。[安装说明](https://herdr.dev/docs/install/)、[v0.9.3 Cargo.toml](https://github.com/herdrdev/herdr/blob/v0.9.3/Cargo.toml)。

## 5. 合仓、统一安装、统一入口要分开验收

| 目标 | 真正要做到 | 仅做到这些还不够 |
|---|---|---|
| 一个 repo | 源码、契约、测试、技能和发布清单同版本维护 | 把目录挪进来但仍靠兄弟 checkout 的绝对路径 |
| 一次安装 | 发布物带齐基础 runtime、技能资产和所选官方扩展；无需手工装本项目的其他仓库 | 只发布 saddle 可执行文件，启动后提示另外装 corral/Python/技能 |
| 一个命令入口 | TUI 与 headless agent CLI 都从 saddle 进入；内部 helper 自动启动 | 要用户先手工运行另一个服务 |
| 单个二进制文件 | 基础 runtime 无外部解释器；必要静态资产嵌入或受控释放 | 仅用 Rust 包一层 Python 子进程 |
| 所有可选扩展也无外部运行时 | 路由、日志、插件依赖也自包含，或明确不属于基础产品 | Corral Rust 化后仍把 Python dlog/route 作为强制流程 |

**统一交付是产品要求，不再以“安装器帮忙装几个独立工具”作为最终方案。** 官方 core plugins 使用 Rust，与 Saddle 同一版本构建、测试、发布；最终不要求用户另外准备本项目的 Python runtime、route.py 或 dlog。

建议优先评估将官方 core plugins 的实现编入 Saddle，由内部入口按需启动独立进程，复用插件协议。这能同时保持一个产品发布物和故障隔离。具体入口、资源布局和是否需要 headless 调用尚未定稿；不能声称现有 manifest 已支持这种内置入口。第三方插件机制保持独立，不因官方内置插件而重写现有 SDK。

## 6. 推荐结构：一个产品，两个方向的扩展

示意布局，名称待定；不要求先搬动 Saddle 当前所有源码：

```text
saddle/
  src/                      # 现有 TUI、CLI 入口与通用插件宿主
  crates/agent-core/        # 最后阶段迁入的 Rust Corral 核心
  crates/plugin-protocol/   # 保留
  crates/plugin-sdk/        # 保留
  plugins/dispatch/        # 先迁入：Rust 派发工具、路由与 skill 资源
  src/telemetry/           # 先实现：宿主记录、SQLite/正文存储与公开查询
  plugins/drover/           # 保留任务插件，改用内置记录接口
  plugins/diff/             # 保留
  skills/corral/            # 基础 agent 操作说明，命令逐步统一
  skills/corral-dispatch/   # 随产品提供的指令资源，调用 Rust 能力
  distribution/            # 发布清单、安装/升级与兼容入口
  docs/
```

先完成外围两个模块；到 Corral 迁移阶段，Python Corral 源码可以原样导入一个明确标为临时的目录，作为行为参照和兼容发布；待 Rust 对等替换后删除，避免永久维护两套实现。建议以 Saddle 为主仓库导入 Corral 历史，保留来源提交与原仓库；不强推重写现有历史。具体采用保留历史的 subtree/merge 导入，在实施前固定导入提交并检查工作树状态。

依赖方向保持简单：TUI/CLI → agent-core；可选工作流/插件 → 公共 agent 操作接口。agent-core 不依赖 Ratatui、Drover、任务文件、模型分档策略或遥测。Saddle 上层组合 agent 调用和可选记录，不向 Corral 核心注入 trace、记录器或遥测回调；迁入后的核心仍可独立构建和测试。插件通过公开接口消费遥测，宿主不反向依赖具体插件。同一个 crate 内先按模块组织，不必为每个概念建 crate 或引入可插拔 backend 框架。

用户侧命令草案（**尚未实现**）：

```text
saddle                          打开界面，按需使用运行核心
saddle agent start/status/...   不打开界面，也能管理 agent
saddle ctl ...                  保留现有实例级界面控制
saddle skills ...               查看/明确安装随版本附带的技能
```

同一 executable 的内部 worker 模式拥有单个 agent 的 PTY；退出 TUI 只断开显示，worker 继续。普通 shell pane 的退出规则先保持当前行为，不借合仓改成全体持久终端。`agent-core` 可先通过统一命令保持现有调用结构，再让确有需要的宿主调用共享 typed client；不在第一次迁移里强行消除所有子进程。

Rust `portable-pty` 提供 PTY 创建、读写和子进程接口，Saddle 已使用 0.9 系列，可以作为复用候选；它不提供 Corral 的投递确认、状态语义、写入者仲裁和升级兼容，不能把“已有库”当成“迁移完成”。[库文档](https://docs.rs/portable-pty/0.9.0/portable_pty/)。Cargo workspace 适合共享锁文件、构建与验证，但本身不解决跨语言发布。[Cargo 官方文档](https://doc.rust-lang.org/cargo/reference/workspaces.html)。

## 7. corral-dispatch 是否应为 core plugin

corral-dispatch 仍按 Rust core plugin 方向设计；遥测改由 Saddle 核心拥有。这里的 core plugin 表示官方内置和统一交付，不意味着重新引入不可绕过的自动任务推进流程。

| 模块 | 自己拥有的职责 | 不应顺带接管 |
|---|---|---|
| Saddle 遥测核心 | 链路/派发身份、证据与版本、SQLite 持久化、正文与历史查询、独立总开关 | 读取 Drover 业务文件、决定下一任务、判断用户是否放行 |
| dispatch | 路由建议及现有派发工具逻辑，调用记录模块与公开 agent 接口，提供 skill 资源 | PTY、agent 状态推断、强制任务阶段 |
| Corral（最后迁移） | agent 生命周期、输入输出、状态、会话身份 | worktree 策略、Git 门槛、任务接受规则 |

推荐在第一阶段内部先落记录模块，再接派发工具：记录是派发和 Drover Dispatch 视图共同使用的基础，先稳定接口可以避免两份业务实现。两个模块是否对应两个运行进程，不由目录数量决定；先保留逻辑分工，再选择最少的运行机制。

Skill 的拆解/审查建议继续作为指令资源；路由工具迁成 Rust，记录按新模型实现。过渡方案由 Saddle agent 薄适配调用公开 Corral CLI，插件不承担遥测包装；Corral 迁入后替换内部调用。结果未知、记录失败或响应丢失都不得导致重复派发。

遥测记录与查询设计为无需 TUI 的一次性 Saddle CLI；不以插件面板或 Drover 启用为前提。完整正文不走受大小限制的 `command.v1`。具体命令仍属草案，首期不引入全局插件 daemon。

## 8. Rust 化的实际难度与必须保留的行为

总体判断：**可控，但属于中高风险的运行核心迁移，不是两千多行的机械翻译。** 与合仓相比，它占主要工作量；不以行数给出“明天一天完成”的承诺。

| 部分 | 难度/回归风险 | 具体原因 |
|---|---|---|
| CLI、JSON、错误码、labels、纯事件解析 | 中 | 可逐项用现有契约和事件 fixture 对照；浮点时间、instance 和缺失字段需一致 |
| PTY、attach、resize、键盘模式 | 高 | bracketed paste、Kitty/修饰键、terminal mode replay、写入者移交、截断转义序列都已有行为 |
| pen 生命周期 | 高 | 锁竞争、重复名字、ready 握手、进程组、分阶段 stop、退出后立即重启同名 agent |
| send/wait/reply | 高 | 写入不等于模型已收到；未提交草稿合并、真人输入保护、超时结果未知、quiet 不等于 idle |
| 四种 agent hook/adapter | 中高 | Claude/Codex 命令 hook 与 pi/omp TypeScript 扩展机制不同；父/子会话、后台任务不能混判 |
| 登录 shell 环境 | 中高 | 当前会重建环境并清理上层 session 标记；安装目录路径和新核心发现信息必须在正确阶段注入 |
| 升级与兼容 | 高 | 新 CLI 遇到旧 pen、旧 hook 继续产生事件、调用方仍使用旧命令/文件位置 |

关键保留项来自现有源码及测试，不是新增业务需求：

1. 一个 client 断开/输出堵塞，不应带走 agent；当前 pen 有输出 ring 和每 client 有界缓冲。保留隔离，不因合仓把它们换成共享无限队列。
2. `send` 的确认依靠输入事件；投递结果未知不能补回车/盲重发。`wait --quiet` 的 stopped-quiet 与 idle 区分。
3. Claude/Codex 退出序列不同，Codex 包含较长的正常退出等待；不能统一成简单 kill。
4. `--after` 的等待与目标都绑定 instance，名字复用不得把消息送给新实例。
5. `env.py` 重建登录 shell 环境，直接继承 TUI 的临时 PATH 不可靠。hook/插件应使用版本化绝对入口或明确注入的宿主路径。
6. hook 必须保持静默、容错，不将内部日志写入 agent 对话。Claude/Codex 当前固定 `/usr/bin/python3 -I -S`；迁移成 Rust hook helper 后才消除此依赖。pi/omp 的扩展脚本由各自 agent 运行时执行，可继续作为资源随版本提供，无须为了“全 Rust”改掉第三方扩展机制。
7. Rust 多线程 TUI 不应直接照搬 Python 的 double-fork 后继续运行应用逻辑。通过独立执行 worker，限定 detach/setsid/文件描述符继承的位置，再建立 ready 握手。

可以复用旧测试的契约、假 agent 和事件 fixture，但一些 Python 测试直接 import 内部实现，不能声称原测试原封不动就覆盖 Rust。需要区分公共黑盒对等检查与移植后的内部单测。

## 9. 不能漏掉的发布与兼容接入

### dispatch-log 的能力由核心遥测替代

现有 dispatch-log 是 Python 程序，Drover Dispatch 视图消费其公开 ls/show/cat；本项目主控当前仍按原指令使用它。新设计不照搬旧 wrapper、脚本 hash 白名单、ID 或数据格式。

首阶段实现 Saddle 自有的记录与查询：SQLite 加内容哈希正文，显式链路关联，保存用户需求依据、实际任务书版本、JEV 请求/完整解析响应/整理建议、主控决策、start/send/reply、审查与返工。Drover 只提供任务关联、默认选择和任务展示。遥测总开关属于 Saddle，停用 Drover 不停用宿主能力。

不做旧数据兼容、导入或双写。旧程序和数据先保留不动；完成新能力和消费者切换后另行退役。不提前把当前 AGENTS.md 中仍有效的记录要求改成尚未实现的命令。

### 最终安装与升级需要交付的结果（Corral 项在最后阶段处理）

- 当前 `~/.local/bin/corral` 指向开发仓库，skill 也存在源码软链接；正式版本应不依赖这些 checkout。开发源码被移动/暂时不可用后，安装版仍能运行。
- 当前 `cargo install --path .` 只安装主程序；Drover/Diff 各自 package.sh 生成包，插件注册还引用目录。统一发布要带插件资产或提供统一安装动作，不让用户手工执行之前那堆 cp/mkdir 命令。
- 可选官方插件可以随包提供，但不能在升级时覆盖用户 manifest 参数、强制重新启用禁用插件或复制真实任务数据。
- 临时兼容入口 `corral` 可以转到同版本 Saddle agent CLI，让旧 skill/脚本继续工作；新安装用户无需认识它。必须实测 argv0/可执行文件路径分流，不能假设一个 symlink 自动改变命令解析。
- 活着的旧 pen 不应被切换程序强行杀掉。候选策略是新客户端保留 v1 连接兼容，旧 pen 自然结束；不是将活着的 Python 进程热变成 Rust。过渡期旧 Python/hook 运行条件仍需保留，等旧实例全部结束才算完成去依赖。
- 稳定入口更新后，旧 agent 的 hook 可能再次执行该路径：采用版本化 helper/资源路径并保留仍被使用的版本，或为新版 hook 命令保持明确兼容。不能升级时删除旧资源。
- 先保留 `CORRAL_HOME`、name/instance、事件和数据位置的兼容策略；不要把合仓同时变成状态目录迁移。上层仍不绕过公共接口读内部文件。
- `saddle ctl` 是界面实例控制，agent CLI 是脱离界面的核心操作，两者不能共用“必须选一个正在运行的 TUI 实例”这一前提。
- worktree 仍然是 Git worktree；合仓不会天然破坏它。需要更新任务模板中的源路径、共享 target、项目根定位，并在更大 workspace 中明确检查包范围。真实历史任务的绝对路径只作为历史引用保留，不自动重写。

## 10. 技术路线比较（实施顺序以外围优先为准）

| 路线 | 直接收益 | 成本与遗留 | 判断 |
|---|---|---|---|
| A. 合仓 + 统一安装，保留 Python Corral | 最快减少用户安装步骤；运行语义变化小 | 要么要求 Python，要么额外打包解释器；Claude/Codex hook 的固定路径仍需处理 | 可作迁移中间态，不宜伪称已达纯二进制目标 |
| B. 合仓 + Rust agent-core + 一个 Saddle 入口，保留每 agent worker | 基础 runtime 自包含、语言/版本统一、核心可 headless 使用 | 先做遥测/dispatch，再做 Corral 契约移植与兼容验证 | **最终建议结构**，按用户要求由外向内迁移 |
| C. 同时改成统一中央 server、插件服务、任务引擎 | 有机会统一所有后台管理 | 生命周期、数据所有权、故障影响、多实例全部重设计 | 此轮不推荐；不是部署要求的必然结果 |

外围迁移阶段允许开发环境仍使用现有 Python Corral，明确标作过渡状态；不能因此宣称完整产品已经自包含。先把 Saddle 遥测与 Rust dispatch core plugin 做完整，再迁移 Corral，最后统一发布目标形态，不长期保留两套同职责实现。

## 11. 后续实施顺序（尚未启动）

顺序已按用户要求确定；遥测接口与切换步骤见专项草案。本轮继续设计，不启动实施。

1. **设计核心遥测与 dispatch 的边界**：按所需数据确定采集接口、开关和公开查询，明确 dispatch 的工具逻辑与 skill 资源。Corral 仓库先完全不动。
2. **实现 Saddle 核心遥测**：覆盖需求依据、完整任务书版本、路由、操作及结果，先用合成数据验证；无需 TUI 或 Drover 的记录/查询入口，不实现旧数据兼容。记录模块不判断任务是否完成。
3. **迁移 corral-dispatch 的工具逻辑到 Rust**：接入内置记录接口，将 skill 随产品提供；继续通过现有 Corral 公开接口执行 agent 操作，保留投递确认与未知结果语义。
4. **清理外围消费者**：Saddle/Drover 的 Dispatch 视图、主控指令和技能入口改用内置能力；退掉外部 route.py/dlog 安装路径依赖。验证既有派发、回复与记录流程，保留真实历史和回退办法。
5. **最后迁移 Corral**：外围只依赖已明确的 agent 操作接口后，再移植 PTY、pen、hooks、状态与 CLI，复用前面稳定的消费者做回归。处理旧 pen/旧 hook 兼容，避免同时改变任务流程。
6. **完成统一发布与真实切换**：证明无需开发 checkout、无需另装本项目其他包/解释器，官方内置能力跟随同一版本升级；按明确的切换方案备份并替换，不关闭用户 agent 或自动修改真实任务。

前两项重点检查：新记录可还原需求与实际任务书版本、独立总开关和显式采集、派发 ID 与 agent instance 关系、start/send/reply 的记录语义、失败/未知结果不重复执行、Drover 正常显示、内置模块无需手工安装、Corral 行为保持原样。Corral 阶段再执行完整 PTY/attach/输入/退出/升级兼容检查。支持平台先对齐现有 Unix 范围，不附带承诺 Windows 支持。

## 12. 已确定与仍需设计

已确定：一个产品统一交付；dispatch 按 Rust core plugin 方向，遥测归 Saddle 核心、可独立关闭；SQLite 加内容哈希正文；不兼容旧日志；外围先做、Corral 最后。本轮仍在设计阶段。

遥测字段、命令、交付顺序与故障行为已收敛为 [接口契约 v1](../任务遥测接口契约.md)，尚未实现。仍需后续处理：官方内置 dispatch 的插件展示/打包机制与 skill 资源安装更新；其路由入口已明确为同进程 headless saddle dispatch route；原始用户需求首期由主控逐字提交是保留来源限制的建议。优先评估同一 Saddle executable 的内部执行入口，避免让用户管理多个包；不把用户已经确定的产品方向重新列成待批准选项。

本轮结论的限制：完成了源码/契约/部署路径调查，没有执行 Rust 原型、吞吐基准、全套测试或真实切换。难度是基于代码和既有行为的工程判断，不是已经测得的迁移工期。
