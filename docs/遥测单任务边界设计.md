# 遥测单任务边界：接口设计

日期：2026-10-02。状态：设计稿，待主控静态核对；未实现、未迁移真实库、未改已安装技能。依据：[DESIGN.md](DESIGN.md)「2026-10-02 单次任务遥测授权边界」和任务《[遥测单任务边界-设计](任务/遥测单任务边界-设计.md)》。本文只核定最小接口变更，不重做遥测；现行事件规则仍以[接口契约 v1](任务遥测接口契约.md)为准。

## 0. 推荐一览

给 trace 增加一个不可逆的“已结束”终态，由新的纯控制命令 `saddle telemetry trace close` 写入。结束等于永久关闭该链路的采集，复用现有 generation 失效机制；之后所有采集入口都按“已关闭”处理，业务照常执行一次。何时结束由主控纪律和绑定方（Drover）决定，宿主只保证结束之后的写入边界。

1. 两级区分：派发级收尾仍是 `controller.note`（note_kind=closure）声明，不改状态；任务级结束只有 `trace close` 一个入口。
2. 调用方：未绑定任务的 ad_hoc trace，由主控在正常收尾的最后一步结束。绑定 Tasks 运行的 task trace，由绑定方 Drover 在 Accept/Return 落盘并追加 transition 后结束，主控不代为结束。
3. 存储：库 user_version 从 1 升到 2，traces 增加 `closed_at`。结束事件复用 `recording.changed`，payload 增加 `closed:true`；用三个触发器保证结束后不能重开、不能再写入。
4. 结束后：create/dispatch/append 和 route/agent 采集一律返回 disabled（code `trace_closed`，退出码 4），业务照常执行一次。`set-recording` 设 true 被拒绝；设 false 或重复 close 返回 duplicate。
5. 升级：新库直接建为 v2；v1 库在新二进制第一次打开写连接时，在同一事务内迁移；读路径不迁移。旧二进制对 v2 库一律返回 unavailable，业务不受影响。
6. 技能资源 revision 从 2 升到 3，随同版本二进制交付，启动时自动升级未改动的已装目标。用户无需新配置，项目 AGENTS 模板不变。

## 1. 结束接口：谁在何时调用什么

### 1.1 两级收尾

| 级别 | 表达 | 含义 | 改变状态 |
|---|---|---|---|
| 派发级 | `controller.note`，note_kind=closure，带 dispatch_id | 某次实现/审查/返工派发实际收尾的声明 | 否，只是未认证声明 |
| 任务级 | `trace close`（新增） | 这次记录授权覆盖的任务已结束，链路之后不再接受任何记录 | 是，不可逆 |

- 链路结束前，closure note 照常可写，可带或不带 dispatch_id。查询不能把它解释为链路已结束；反过来，链路结束也不证明任何派发成功、通过验收或已合并。
- 历史 closure note（包括 Theme 链路）保持原义，不自动解释为链路结束，也不补写结束。

### 1.2 谁调用、何时调用

- **origin=ad_hoc（口头任务，未绑定外部任务）由主控结束。** 正常收尾的最后一步：把实际合并、清理、构建、推送结果写入 closure note 后，执行 `trace close`。任务按约停在审查、用户放弃或明确停止时，在向用户报告最终结果后结束。如果任务还在等用户对它的决定（例如停在审查，等用户决定是否合并），就是尚未完成，不结束；用户的决定来了，先在同一 trace 记录，再结束。
- **origin=task（声明绑定外部任务运行的 trace，目前即 Drover 的 `drover.task`）由绑定方结束。** 本 run 的终态流转（Accept→done、Return→pending）业务落盘、追加 task.transition 之后，Drover 调用 `trace close`。主控收尾时只写 closure note，不结束这类链路，否则会截掉之后的人工流转。Submit（→awaiting_release）不是终态，不结束。
- 宿主不判断任务是否完成：不读聊天，不依据 agent idle、DONE 或 Git 提交，也不监听会话。只有上述调用方显式调用时，链路才结束。
- “任务”指用户这次要求记录时所指的那件工作，可以拆成多个派发或多个任务文件；它不是会话、项目或主题。边界由主控判断，并在 closure note 写明这次收尾覆盖的范围。用户之后的另一项独立要求，即使属于同一主题，默认也不记录；再次要求记录就新建 trace。

### 1.3 结束后各入口的响应

拒绝在写事务前或事务内复核时发生，不读正文、不写任何事件，也不改变业务调用本身。

| 入口 | 结束后的结果 | 业务 |
|---|---|---|
| `trace create`（用同一 ID 重交） | disabled / trace_closed，退出 4 | 纯记录；新的记录要求用新 UUID 建新 trace |
| `dispatch create` | disabled / trace_closed，退出 4 | 纯记录；主控按“业务前唯一降级点”说明没有上下文，然后继续 |
| `append`（含 task.transition、note、复用证据） | disabled / trace_closed，退出 4；不读取正文文件 | 纯记录，没有业务 |
| `saddle agent … --record-context <旧上下文>` | 预检返回 disabled（不是 invalid），不会以 125 拒绝；回执 begin/end=disabled | 照常执行一次，不重发；executed 按实际业务 |
| `saddle plugin run dispatch route --record-context <旧上下文>` | 同上，begin/end=disabled | 路由照常返回 |
| 结束前已 prepare 的在途 Capture（record_begin/record_end） | disabled；该 operation 已保存的部分保留，end 永久缺失 | 业务结果仍由执行入口原样返回 |
| `trace set-recording`，enabled=true | disabled / trace_closed，退出 4；不会重开 | — |
| `trace set-recording`，enabled=false | duplicate，退出 0 | — |
| 再次 `trace close` | duplicate，退出 0 | — |
| list/show/events/body | 照常可查，多一个 closed_at | — |

`check_operation` 遇到已结束链路必须返回 disabled 类错误，不能返回 invalid。现有 agent/plugin 入口只在 invalid 时拒绝执行（`src/agent.rs:352`、`src/plugins/capture.rs:124`），因此不用改分支，业务就会照常执行一次。

### 1.4 宿主强制、调用方纪律与尽力而为

| 宿主强制（代码和库触发器） | 主控纪律（技能写明，宿主无法验证） | Drover（插件代码，尽力而为） |
|---|---|---|
| 结束不可逆：当前二进制都不能再在该 trace 新增 dispatch、事件或 operation，也不能重开 | 判断任务边界和完成时间；ad_hoc 链路在正常收尾时调用 close | Accept/Return 落盘并追加 transition 后调用 close |
| 结束后使用旧上下文只得到 disabled，不会被拒绝执行 | 不结束 origin=task 链路 | 失败只在结果的 telemetry 中报告，不重试，不影响业务 |
| close 不需要总开关开启，不建库，不带正文 | 结束后不再使用本次 ID；下一项任务未要求就不记录，要求了就新建 trace | 不为 close 改状态机或队列动作 |
| 旧二进制拒绝读写 v2 库 | 不按“最新 trace”恢复，不复用已结束的 trace | |

宿主无法强制以下几点：主控按时调用 close；一个尚未结束的 trace 只用于本任务；用户确实提出过记录要求（来源都是未认证声明）。漏调 close 的后果是 trace 一直开放，在查询页显示 `recording on`；主控可事后按 ID 结束（幂等）。

## 2. 状态、存储、接口与并发

### 2.1 存储：schema v2

- traces 增加 `closed_at TEXT`（NULL 表示未结束，取值为 UTC RFC3339）。新库在 schema.sql 中把它放在 traces 最后一列；迁移库用 `ALTER TABLE traces ADD COLUMN closed_at TEXT`，两者结构一致。
- 库版本 `PRAGMA user_version=2`。输入 JSON 的 `schema_version` 仍为 1（新命令也用 1），与库版本互不相干。
- 三个触发器，迁移库与新建库相同：
  1. traces：`BEFORE UPDATE OF capture_enabled,generation,closed_at`，`WHEN OLD.closed_at IS NOT NULL` 时 ABORT，结束后既不能重开，也不能再改 generation。
  2. events：`BEFORE INSERT`，当 NEW.trace_id 指向已结束的 trace 时 ABORT。
  3. dispatches：同样的 `BEFORE INSERT` 保护。operation 行只在写 begin/end 事件的同一事务内插入，会随触发器 2 一起回滚。
- 不新增事件类型。events.kind 是表级 CHECK，要加类型就得重建只追加、带不可变触发器的 events 表，等于重写历史，因此不采用。结束事件复用 `recording.changed`（T 作用域、system_control、无正文），payload 为 `{enabled:false, generation, actor, changed_at, closed:true}`。`closed` 只由结束路径写入，取值只有 true。

### 2.2 结束事务：`Store::close_trace`

1. 用 `writer(false)` 打开，不初始化。没有库或 trace 不存在时返回 invalid（unknown trace_id），退出 2。
2. 在一个 BEGIN IMMEDIATE 事务内读取 closed_at；已结束则返回 duplicate。
3. 未结束时，先插入上述 recording.changed（generation 为当前值加 1），再执行 `UPDATE traces SET capture_enabled=0, generation=generation+1, closed_at=<now>`，然后提交。先写事件、后置 closed_at，触发器 2 就不会拦住结束事件本身。
4. 不检查总开关。结束只减少采集，属于开关控制；与现有 set-recording 一样，总开关关闭时也能执行。不读正文，不建 trace 或 dispatch。
5. 已暂停（capture_enabled=0）的 trace 也按此结束；开关区间不变，只多一个结束点。

### 2.3 公开接口

- Rust：`Store::close_trace(TraceCloseInput) -> Result<Value>`。`TraceCloseInput{schema_version, trace_id, actor}` 使用 deny_unknown_fields，actor 是未认证声明。
- CLI：`saddle telemetry trace close --input FILE|-`，输入为 `{"schema_version":1,"trace_id":"TRACE","actor":"controller"}`。回执沿用纯记录格式：stored/duplicate（退出 0）、invalid（2）、unavailable（1），不会返回 disabled 或 conflict。`--help` 增加一行。
- 新错误 `Error::closed()`：status 为 `disabled`，code 为 `trace_closed`，沿用退出码 4。`storage::policy/enabled` 读取 trace 策略时先判断 closed_at，所以 create_trace、create_dispatch、append、check_operation、prepare_operation、record_begin、record_end 都会自动得到这个错误。`change_recording` 对已结束 trace：enabled=true 返回 trace_closed，false 返回 duplicate。
- 不新增 status、退出码或回执字段，现有消费者（Drover 的状态映射、技能中的回执说明）对 disabled 的处理继续成立。agent/plugin 回执的 begin/end 只写 status，即 `disabled`；要区分是全局关闭还是链路已结束，用 `show --id TRACE` 查看 closed_at。

### 2.4 幂等、并发与在途操作

- **幂等**：按状态判重，不需要调用方提供事件 ID。重复或并发 close 只有一次 stored，其余为 duplicate。
- **与写入并发**：append、dispatch create 和采集都在 IMMEDIATE 写事务内复核 trace 策略（append 和 record_* 已经是“读阶段固定 generation，写事务内再比较”）。close 先提交，对方得到 trace_closed，不发布正文；对方先提交，那条记录属于结束之前，予以保留。暂存目录可能留下已读取但未发布的字节，这与现有关闭语义相同，不承诺擦除。
- **在途操作**：close 不等待任何 end。结束前已写 begin 的 operation，结束后不能再写 end，在 `show` 里 end_missing 永久为 true。结束后不能再插入 operation 或事件，所以查询看到的缺 end 集合就是结束那一刻的集合，不需要另存清单。崩溃残留（只有 begin、进程已不在）不会阻塞结束，事后也不会被补成 end；不设补写 end 的宽限期。
- 正常流程下，主控在自己发起的调用全部返回、agent 已停之后才结束，在途 operation 只会来自崩溃或误用。
- **总开关**：close 不会开启任何东西。已结束的 trace 即使总开关打开也不再采集；总开关关闭也不妨碍 close。
- **实现注意**：`policy()` 既被 reader（库可能仍是 v1）也被 writer 调用，需要按库版本决定是否读取 closed_at。

### 2.5 查询与显示

- `list` 和 `show(trace)` 的每条 trace 增加 `closed_at`（string 或 null）。`recording_intervals` 会在结束事件处自然截止，算法不用改；`operations` 不变。
- 历史 trace 的 closed_at 为 null，显示与现在相同；历史 closure note 不参与判断。
- 宿主 Telemetry 页只改英文状态文字，不改布局：
  - 列表在 `trace paused` 之外增加 `trace ended`；
  - 底部的 `trace recording on|paused` 增加 `ended <closed_at>`；
  - 详情计数行在链路结束后把 `recording on|off` 写成 `recording ended`；
  - 带 closed 的 recording.changed 事件显示为 `Trace ended`；
  - 已结束 trace 的缺 end 计数照旧写 `no end`，不推断原因。
- Drover 的 Run details、通知和报告不改，不从链路结束推断任务成功或已验收。

## 3. v1 库升级、旧 trace、旧二进制与部署顺序

### 3.1 读写升级

- **没有库**：settings/list/show/events/body 照旧返回 `initialized:false`，不建目录。`trace close` 返回 invalid（unknown trace_id），不建库。第一次初始化（settings set）直接建 v2。
- **读**：新二进制的 reader 接受版本 1 和 2；遇到 v1 时把 closed_at 视为 NULL（查询按版本选用 `closed_at` 或 `NULL`）。**读路径从不迁移**：Settings 打开、Telemetry 页、Drover 读取报告都保持只读。
- **写**：`writer()` 打开 v1 库时，在同一个 IMMEDIATE 事务内复核 user_version，然后加列、建三个触发器、设 user_version=2。两个进程并发迁移时，后到者读到 2 就跳过。迁移共用现有 100 ms 等锁预算；失败就回滚并返回 unavailable，各业务入口按“存储不可用”处理，不重放。新二进制的任何写连接都会触发迁移，包括随后因总开关关闭而返回 disabled 的调用；迁移只改结构，不写记录。
- **不重写历史**：既有的行、事件、正文和链接都不改。历史 trace 的 closed_at=NULL，即“未结束”。Theme 等旧 trace 不会自动结束，本任务也不操作；是否结束交给用户另行决定。
- **实现注意**：`create_trace` 现在用位置式 `INSERT INTO traces VALUES(?,?,?,1,0,…)`（`src/telemetry/storage.rs:254`），加列后必须改为按列名插入。

### 3.2 旧二进制的限制

- 迁移后，旧二进制（只接受 v1）读写都返回 unavailable（unsupported database version）：旧 Settings 显示 Unknown，旧 Telemetry 页报错，旧 Drover 回到 no_context 直接发送，旧 `saddle agent`/plugin 采集 unavailable 而业务照常执行一次。数据不受损。
- 迁移那一刻已经打开连接的旧进程：之后向已结束 trace 的写入被触发器拒绝；按位置向 traces 插入会因列数不符而失败。两者都表现为 unavailable，不会留下写了一半的记录。
- 不提供降级工具。退回旧版时，要么接受遥测不可用，要么恢复迁移前的一致性快照（快照之后的新记录会丢失）。

### 3.3 实际部署顺序（需另行授权，本轮不执行）

1. 宿主（Store v2、close、显示）、Drover close、技能 revision 3 和文档放在同一个集成分支，审查后一起合并；不先发技能再发命令。
2. 用户退出日常 Saddle，并确认没有进行中的 `saddle agent`/`plugin run` 记录调用。
3. 备份旧宿主和 Drover 包；按备份边界取得遥测库的一致性快照（SQLite backup；正文不可变，无需处理）。
4. 可选：在快照副本上用新二进制（临时 XDG_STATE_HOME）验证——v1 可只读访问，第一次写入后迁移到 2，历史 trace 的 closed_at 为 null，历史 closure 仍是 note。不为验证去写真实库。
5. 成套替换宿主和 Drover 包，然后启动 Saddle。已启用的 dispatch 插件会在启动时把自有且未改动的 corral-dispatch 从 revision 2 升级到 3；`saddle plugin status dispatch` 应显示两个目标 owned_current、revision 3。被改动或有冲突的目标只报告、不覆盖，用户处理后再执行 Sync resources。
6. 真实库在下一次正常写入时迁移；部署本身不为验证而写库。
7. 已在运行的主控会话不会自动刷新已加载的文本。项目 AGENTS 规定“本链路选择记录时先读遥测操作.md”，所以下次选择记录时会读到 revision 3。部署前已在记录、未按新规结束的链路保持开放并在查询页显示，可事后按 ID 结束。

## 4. 口头链路与 Tasks run 的衔接

| 场景 | 谁建 trace | 主控段 | 人工验收/退回段 | 谁结束、何时 |
|---|---|---|---|---|
| 口头任务，没有 Tasks run | 用户明确要求后，主控建 ad_hoc trace | 委派、执行、返工、审查、closure note | 用户对同一任务的后续决定（如是否合并）由主控在同一 trace 转录 | 主控，在实际收尾后 |
| Tasks run，派发时选了记录 | Drover（现有 04B） | 用交付附段里的上下文记录；收尾写 closure note，不结束链路 | Submit/Accept/Return：Drover 业务落盘后追加 task.transition，Return 带原因正文 | Drover，在 Accept 或 Return 的 transition 之后 |
| Tasks run 没选记录，用户中途口头要求记录 | 主控经 Drover 公开接口核实 task/run 后，建 origin=task、带完整 binding 的 trace（coverage_start 是实际开始记录的时间） | 同上 | Drover 按完整 binding 找到该 trace 并追加 | Drover |
| Return 后重新派发 | 新 run 由 Drover 按记录选择建新 trace | 在新 trace 记录；需要时用 evidence.reused 显式引用旧需求 | 旧 run 的退回原因在结束前已写入旧 trace，Drover 历史中也有 | 新 run 的 Accept/Return |

- **Drover 的结束顺序**：业务落盘 → 追加 transition（Return 附原因）→ close。原因在结束前写入，不会因结束而丢失。如果 transition 因存储故障没写进去，原因仍保存在 Drover 自己的数据和 Run details 的退回历史里，遥测缺口在结果中报告。
- **无论 transition 结果如何都尝试 close**：run 已经终结，保持开放只会留下可被误用的窗口。如果找不到该 run 的 trace（not_recorded）或查询失败，则不 close，`telemetry.close` 记 not_attempted。
- **预算与结果**：close 使用单独的短预算（建议 300 ms，与身份创建预算一致），在现有 transition 之后、返回结果之前执行。结果另加 `telemetry.close`（stored/duplicate/disabled…/not_attempted），不改 delivery/record，不重试，也不改状态机、队列动作或通知。
- **口头任务不要求登记 Tasks**：只有本来就存在 Drover run 时才绑定它。如果主控对已有的 Drover run 另建 ad_hoc trace，Drover 找不到它，人工流转就记不下来，所以技能要求“有 run 就绑定 run”。

### 4.1 与本次要求的实质冲突（列出，不自行豁免）

- **C1 退回后重新派发的“同任务返工”**：用户规则把返工算在本次任务内，但在 Drover 里，Return 后再派发是新 run。现行设计按项目默认或本次勾选决定是否记录；如果只在首次派发时勾选，再派发时用户得再勾一次，相当于对同一任务“再次要求”。推荐：对“上一 run 请求过记录、且以 Return 结束”的任务，Drover 把再派发的 Record 默认设为开（界面可见、可以取消），机制只在 Drover 自己的数据和界面内，宿主不变。需用户确认后才实施，确认前保持现状。
- **C2 Drover 项目默认 `TELEMETRY_RECORD=on`**：它让之后每次派发都记录，而不是“一次要求对应一项任务”。但它是用户显式设置、界面可见、随时可关的常设选择；每个 run 仍各自新建 trace，并在 Accept/Return 时结束，不会延长已结束的链路。推荐保留，视为“用户已要求记录”的一种形式；需用户确认这一理解。

## 7. 已批准规则与待裁定取舍

**已批准**（DESIGN 2026-10-02 及用户原话）：
- 一次授权覆盖当前任务的委派、执行、返工、审查和实际收尾；之后默认不记录，再次要求则新建 trace；
- 用户不必说停止，不必提供 ID，也不必登记 Tasks；
- 主控在正常收尾中结束链路；宿主不从聊天、idle、DONE 或 Git 推断任务完成；
- closure note 只是声明；
- 总开关语义不变；只重试记录，不重做业务；
- Submit/Accept/Return 保持人工操作；
- 宿主保持通用，不依赖插件；不改 Corral。

**待主控裁定的实现取舍**（括号内为本文推荐的理由）：
- I1 采用库 v2 + closed_at 列 + 触发器（不迁移、从事件推导的方案下，旧二进制会无视结束继续写）。

- I5 绑定的 trace 由绑定方结束，主控不代为结束；Drover 在 Accept/Return 后，不论 transition 结果如何都尝试 close，使用单独的 300 ms 预算。
- I6 迁移在新二进制第一次打开写连接时进行，读不迁移。
- I7 主控把 ad_hoc 的 trace_id 写进任务文件，便于恢复和结束。
