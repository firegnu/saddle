> 已退役（2026-10-05）：Saddle 已删除遥测、Drover 和整个插件系统。本文只保留设计/验证历史，不再作为当前操作规矩或安装指引；旧磁盘数据不读、不删。当前功能与命令见 [README](../README.zh-CN.md)，派发路由由 ranch 提供。

日期：2026-10-02。状态：1074b3a经主控静态复核通过，M1–M3关闭，I1–I8已定稿；未实现、未迁移真实库、未改已安装技能。本设计核对不是安装或部署授权。依据：[DESIGN.md](DESIGN.md)「2026-10-02 单次任务遥测授权边界」和任务《[遥测单任务边界-设计](任务/遥测单任务边界-设计.md)》。本文只核定最小接口变更，不重做遥测；现行事件规则仍以[接口契约 v1](任务遥测接口契约.md)为准。

## 0. 推荐一览

给 trace 增加一个不可逆的“已结束”终态，由新的纯控制命令 `saddle telemetry trace close` 写入。结束等于永久关闭该链路的采集，复用现有 generation 失效机制；之后各写入和采集入口都按“已关闭”处理，原本合法的业务调用照常执行一次。何时结束由主控纪律和绑定方（Drover）决定，宿主只保证结束之后的写入边界。

1. 两级区分：派发级收尾仍是 `controller.note`（note_kind=closure）声明，不改状态；任务级结束只有 `trace close` 一个入口。
2. 调用方：
   - 未绑定任务的 ad_hoc trace，由主控在本次授权所指任务实际完成并交付后结束。
   - 绑定 Tasks run 的 task trace，由绑定方 Drover 在 Accept/Return 落盘并尝试追加 transition 后结束，主控不代为结束。
   - 同一 run 内的实现/审查返工都留在同一 trace；Return 结束该 run，之后再派发是新 run，按 Tasks 已有规则决定是否新建 trace。
3. 存储：库 user_version 从 1 升到 2，traces 增加 `closed_at`。结束事件复用 `recording.changed`，payload 增加 `closed:true`；用三个触发器保证结束后不能重开、不能再写入。
4. 读写分开：只读的策略读取（show、set-recording 的幂等判断）照常返回状态，不因结束报错。只有写入和采集的开关判定才拒绝，status 为 disabled；trace 行存在且已结束时，code 优先报 `trace_closed`。格式或关联本身无效的输入，仍在各入口原来的位置被拒绝，结束不会让它们绕过校验。
5. 升级：新库直接建为 v2；v1 库在新二进制第一次打开写连接时，在同一事务内迁移；读路径不迁移。旧二进制对 v2 库一律返回 unavailable，业务不受影响；不提供降级。
6. 技能资源 revision 从 2 升到 3，随同版本二进制交付，启动时自动升级未改动的已装目标。用户无需新配置，项目 AGENTS 模板不变。

## 1. 结束接口：谁在何时调用什么

### 1.1 两级收尾

| 级别 | 表达 | 含义 | 改变状态 |
|---|---|---|---|
| 派发级 | `controller.note`，note_kind=closure，带 dispatch_id | 某次实现/审查/返工派发实际收尾的声明 | 否，只是未认证声明 |
| 任务级 | `trace close`（新增） | 这次记录授权覆盖的任务已结束，链路之后不再接受任何记录 | 是，不可逆 |

- 链路结束前，closure note 照常可写，可带或不带 dispatch_id。查询不能把它解释为链路已结束；反过来，链路结束也不证明任何派发成功、通过验收或已合并。
- 历史 closure note 保持原义，不会被自动解释为链路结束，也不会补写结束。历史 trace（包括 Theme 链路）不在本设计的操作范围内。

### 1.2 谁调用、何时调用

**结束条件**：本次授权所指的任务确实完成并交付，且同一任务没有待决事项；或者用户明确放弃、终止这项任务。

- 某一阶段的产出不是全任务的终点，例如一轮设计稿、一次审查结论、一个实现候选。
- 任务书约定只做到某一步的，交付了这一步的结果、并且同一任务没有待用户决定的事项，才算完成。
- 同一任务还在等用户决定（是否合并、是否继续、是否返工等），就是没有完成，不结束。决定来了，先在同一 trace 记录，再按结果继续或结束。

**谁调用**：

- **origin=ad_hoc（口头任务，未绑定外部任务）由主控结束。** 在正常收尾的最后一步执行：实际合并、清理、构建、推送结果写入 closure note 之后，调用 `trace close`。
- **origin=task（声明绑定外部任务运行的 trace，目前即 Drover 的 `drover.task`）由绑定方结束。** 本 run 的终态流转（Accept→done、Return→pending）业务落盘、尝试追加 task.transition 之后，Drover 调用 `trace close`。主控收尾时只写 closure note，不结束这类链路，否则会截掉之后的人工流转。Submit（→awaiting_release）不是终态，不结束。
- 宿主不判断任务是否完成：不读聊天，不依据 agent idle、DONE 或 Git 提交，也不监听会话。只有上述调用方显式调用时，链路才结束。
- **“任务”的范围**：用户这次要求记录时所指的那件工作，可以拆成多个派发或多个任务文件；它不是会话、项目或主题。边界由主控判断，并在 closure note 写明这次收尾覆盖的范围。用户之后的另一项独立要求，即使属于同一主题，默认也不记录；再次口头要求记录就新建 trace。

### 1.3 结束后各入口的响应

下表假定输入格式和关联本身有效。无效输入在各入口原来的位置照旧被拒绝（见 2.3 的判定顺序）；结束只影响原本会进入开关判定的调用。

| 入口 | 结束后的结果 | 业务 |
|---|---|---|
| `trace create`（用同一 ID 重交） | disabled / trace_closed，退出 4 | 纯记录；新的记录要求用新 UUID 建新 trace |
| `dispatch create` | disabled / trace_closed，退出 4 | 纯记录；主控按“业务前唯一降级点”说明没有上下文，然后继续 |
| `append`（含 task.transition、note、复用证据） | disabled / trace_closed，退出 4；不读取正文文件 | 纯记录，没有业务 |
| `saddle agent … --record-context <原本合法的旧上下文>` | 预检先校验关联（无效则照旧以 125 拒绝），再判开关得到 disabled；回执 begin/end=disabled | 照常执行一次，不重发；executed 按实际业务 |
| `saddle plugin run dispatch route --record-context <原本合法的旧上下文>` | 同上，begin/end=disabled | 路由照常返回 |
| 结束前已 prepare 的在途 Capture（record_begin/record_end） | disabled / trace_closed；该 operation 已保存的部分保留，end 永久缺失、结果保持未知 | 业务结果仍由执行入口原样返回 |
| `trace set-recording`，enabled=true | disabled / trace_closed，退出 4；不会重开 | — |
| `trace set-recording`，enabled=false | duplicate，退出 0（只读策略读到已关闭） | — |
| 再次 `trace close` | duplicate，退出 0 | — |
| `trace close`：没有库或 trace 不存在 | invalid（unknown trace_id），退出 2；不建库 | — |
| list/show/events/body | 照常可查，多一个 closed_at，区间按 2.5 截止 | — |

现有 agent/plugin 入口只在 invalid 时拒绝执行（`src/agent.rs:352`、`src/plugins/capture.rs:124`），而 `check_operation` 先校验关联、后判开关（`src/telemetry/capture.rs:138`）。因此，原本合法的旧上下文遇到已结束链路，得到的是 disabled 类结果，业务照常执行一次；原本无效的上下文照旧被拒绝。

### 1.4 宿主强制、调用方纪律与尽力而为

| 宿主强制（代码和库触发器） | 主控纪律（技能写明，宿主无法验证） | Drover（插件代码，尽力而为） |
|---|---|---|
| 结束不可逆：当前二进制都不能再在该 trace 新增 dispatch、事件或 operation，也不能重开 | 判断任务边界与是否完成；ad_hoc 链路在本次任务完成并交付后调用 close | Accept/Return 落盘并尝试追加 transition 后调用 close |
| 结束后，原本合法的旧上下文只得到 disabled，不会被拒绝执行 | 不结束 origin=task 链路 | transition 或 close 失败只在结果的 telemetry 中报告，不重试，不影响业务；遥测中可能永久缺这条记录 |
| close 不需要总开关开启，不建库，不带正文 | 结束后不再把本次 ID 带给后续命令；下一项任务未要求就不记录，要求了就新建 trace | 不为 close 改状态机或队列动作 |
| 只读查询不受结束影响；旧二进制拒绝读写 v2 库 | 不按“最新 trace”恢复，不复用已结束的 trace | |

宿主无法强制以下几点：主控按时调用 close；一个尚未结束的 trace 只用于本任务；用户确实提出过记录要求（来源都是未认证声明）。漏调 close 的后果是 trace 一直开放，在查询页显示 `recording on`；主控可事后按 ID 结束（幂等）。

## 2. 状态、存储、接口与并发

### 2.1 存储：schema v2

- traces 增加 `closed_at TEXT`（NULL 表示未结束，取值为 UTC RFC3339）。新库在 schema.sql 中把它放在 traces 最后一列；迁移库用 `ALTER TABLE traces ADD COLUMN closed_at TEXT`，两者结构一致。
- 库版本 `PRAGMA user_version=2`。输入 JSON 的 `schema_version` 仍为 1（新命令也用 1），与库版本互不相干。
- 三个触发器，迁移库与新建库相同：
  1. traces：`BEFORE UPDATE OF capture_enabled,generation,closed_at`，`WHEN OLD.closed_at IS NOT NULL` 时 ABORT，结束后既不能重开，也不能再改 generation。
  2. events：`BEFORE INSERT`，当 NEW.trace_id 指向已结束的 trace 时 ABORT。
  3. dispatches：同样的 `BEFORE INSERT` 保护。operation 行只在写 begin/end 事件的同一事务内插入，会随触发器 2 一起回滚。
- 不新增事件类型。events.kind 是表级 CHECK，要加类型就得重建只追加、带不可变触发器的 events 表，等于重写历史，因此不采用。
- 结束事件复用 `recording.changed`（T 作用域、system_control、无正文），payload 为 `{enabled:false, generation, actor, changed_at, closed:true}`。`closed` 只由结束路径写入，取值只有 true；每条 trace 至多一条（由触发器 1 保证）。

### 2.2 结束事务：`Store::close_trace`

1. **只读预查**：用 `reader()` 打开。没有库时返回 invalid（unknown trace_id），退出 2，不建目录。这一步必须显式做，因为 `writer(false)` 在没有库时返回的是 disabled（与现有 `change_recording` 对 trace 的预查同理）。
2. 用 `writer(false)` 打开，不初始化；遇到 v1 库按 3.1 迁移。
3. 在一个 BEGIN IMMEDIATE 事务内用只读策略读取 trace 行：不存在 → invalid；closed_at 非空 → duplicate。
4. 未结束时，取一个时间戳 T。先插入上述 recording.changed（changed_at=T，generation 为当前值加 1），再执行 `UPDATE traces SET capture_enabled=0, generation=generation+1, closed_at=T`，然后提交。先写事件、后置 closed_at，触发器 2 就不会拦住结束事件本身；closed_at 与结束事件的 changed_at 是同一个值。
5. 不检查总开关。结束只减少采集，属于开关控制；与现有 set-recording 一样，总开关关闭时也能执行。不读正文，不建 trace 或 dispatch。
6. 已暂停（capture_enabled=0）的 trace 也按此结束。

### 2.3 只读策略与写入判定

**只读策略 `policy()`**：返回 `(capture_enabled, generation, closed_at)`，不因结束而报错，只在 trace 不存在时返回 invalid（现状）。使用方：

- `show`（`src/telemetry/query.rs:365`）；
- `change_recording` 的当前值读取（`src/telemetry/storage.rs:191`）；
- close 的状态读取。

reader 打开的可能仍是 v1 库，此时按版本把 closed_at 读作 NULL。

**写入判定 `enabled()`**（或改名为单独的写入门）只用于创建、追加和采集：create_trace、create_dispatch、append 的读阶段与写事务、check_operation、prepare_operation、record_begin、record_end。依次判定：

1. 给定 trace 且该行存在、closed_at 非空 → disabled / `trace_closed`。这一步排在全局开关之前，所以总开关关闭时也报 trace_closed。
2. 全局关闭 → disabled / `recording_disabled`（现状）。
3. trace 不存在 → invalid（现状）；trace 暂停 → disabled / `recording_disabled`（现状）。

第 1 步只在 trace 行存在时生效，不存在的 trace 仍按现有顺序报告（总开关关闭时为 disabled，开启时为 invalid），不改变其他情况的现有结果。写事务内的二次复核也走这个判定：读阶段之后才结束的，报 trace_closed；其他 generation 变化仍报 recording_disabled。create_trace 遇到已存在的同 ID 时，同样先走第 1 步。

**与输入校验的先后**：保持各入口原有位置，不前移、不后移。

- 语法和字段校验在所有入口都最先进行。
- `check_operation` 先校验关联，再判开关：无效关联照旧 invalid（agent/plugin 以 125 拒绝），有效关联才会得到 trace_closed。
- append 原本是先判开关、再校验关联，结束后的 append 报 trace_closed。它只是纯记录，没有业务。

**`change_recording` 对已结束 trace**：enabled=false 时，当前值已是 false，返回 duplicate；enabled=true 时返回 trace_closed。全局 set-recording 不变。

**公开接口**：

- Rust：`Store::close_trace(TraceCloseInput) -> Result<Value>`。`TraceCloseInput{schema_version, trace_id, actor}` 使用 deny_unknown_fields，actor 是未认证声明。
- CLI：`saddle telemetry trace close --input FILE|-`，输入为 `{"schema_version":1,"trace_id":"TRACE","actor":"controller"}`。回执沿用纯记录格式：stored/duplicate（退出 0）、invalid（2）、unavailable（1），不会返回 disabled 或 conflict。`--help` 增加一行。
- 新错误 `Error::closed()`：status 为 `disabled`，code 为 `trace_closed`，沿用退出码 4。不新增 status、退出码或回执字段，现有消费者对 disabled 的处理继续成立。agent/plugin 回执的 begin/end 只写 status，即 `disabled`；要区分是全局关闭还是链路已结束，用 `show --id TRACE` 查看 closed_at。

### 2.4 幂等、并发与在途操作

- **幂等**：按状态判重，不需要调用方提供事件 ID。重复或并发 close 只有一次 stored，其余为 duplicate。
- **与写入并发**：append、dispatch create 和采集都在 IMMEDIATE 写事务内复核写入判定（append 和 record_* 已经是“读阶段固定 generation，写事务内再比较”）。close 先提交，对方得到 trace_closed，不发布正文；对方先提交，那条记录属于结束之前，予以保留。暂存目录可能留下已读取但未发布的字节，这与现有关闭语义相同，不承诺擦除。
- **在途操作**：close 不等待任何 end。结束前已写 begin 的 operation，结束后不能再写 end，在 `show` 里 end_missing 永久为 true，结果保持未知。结束后不能再插入 operation 或事件，所以查询看到的缺 end 集合就是结束那一刻的集合，不需要另存清单。只有 begin、进程已不在的崩溃残留不会阻塞结束，事后也不会被补成 end；不设补写 end 的宽限期。
- 缺 end 的原因可能是崩溃、超时或取消、存储暂不可用、与 close 并发等，查询不推断是哪一种。
- **正常收尾的顺序**：主控先等本任务自己发起的公开调用（route/start/send/reply）返回，自己开的实施和审查会话按项目正常生命周期处理，然后再 close。不为 close 停止主控会话或用户的 agent，也不要求被保留的会话全部消失。
- **总开关**：close 不会开启任何东西。已结束的 trace 即使总开关打开也不再采集；总开关关闭也不妨碍 close。

### 2.5 查询与显示

**结束后的区间投影**（修改 `trace_details`，`src/telemetry/query.rs:140-184`）：

- 现有算法读取本 trace 和所有全局的 recording.changed，按 seq 遍历，最后无条件追加一个 end=null 的区间；之后的全局开关变化也会继续产生区间。只把结束事件当作 enabled=false 处理，会留下无限延伸的 off 尾段，所以必须改。
- 未结束的 trace：算法完全不变。
- 已结束的 trace：先取本 trace 结束事件（`trace_id` 为本 trace、payload `closed:true`）的 seq，记为 S。只有 seq ≤ S 的控制事件参与投影，也只有它们列入 show 的 `recording_history`。
- 遍历到结束事件时，无条件输出终止区间 `{start, end: 结束事件的 changed_at, enabled: 结束前的 global && local}` 并停止，不再追加 end=null 的区间。这个终止区间不受现有 `time > created` 条件约束，所以投影一定以有界区间收尾。
- 截止按 seq，不按时间：机器时钟回拨或跳变不会把结束前的历史误丢，也不会把结束后的全局变化算进来。时间按存储原样输出，不重排。
- 结束前事件仍沿用现有的 `time > created` 处理，不扩展通用时间算法。
- 原始事件查询（events）与其他 trace、全局开关的行为不变；结束后的全局 recording.changed 照常存在，只是不再投影到已结束 trace 上。
- 晚交判定 `decorate_event` 不用改：结束事件是 enabled=false，不会移动记录时段的起点，而且结束后无法再追加事件。

**字段**：`list` 和 `show(trace)` 的每条 trace 增加 `closed_at`（string 或 null），其值等于结束事件的 changed_at。`operations` 不变。历史 trace 的 closed_at 为 null，显示与现在相同；历史 closure note 不参与判断。

**宿主 Telemetry 页**：只改英文状态文字，不改布局。

- 列表在 `trace paused` 之外增加 `trace ended`。
- 底部的 `trace recording on|paused` 增加 `ended <closed_at>`。
- 详情计数行在 closed_at 非空时写 `recording ended`。它必须按 closed_at 判断，不能看最后一个区间：终止区间的 enabled 可能为 true，表示的是结束前那一段。
- 区间视图里，已结束的 trace 不再出现 `now`。
- 带 closed 的 recording.changed 事件显示为 `Trace ended`。
- 已结束 trace 的缺 end 计数照旧写 `no end`，不推断原因。

Drover 的 Run details、通知和报告不改，不从链路结束推断任务成功或已验收。

## 3. v1 库升级、旧 trace、旧二进制与部署顺序

### 3.1 读写升级

- **没有库**：settings/list/show/events/body 照旧返回 `initialized:false`，不建目录。`trace close` 由 2.2 的只读预查返回 invalid，不建库。第一次初始化（settings set）直接建 v2。
- **读**：新二进制的 reader 接受版本 1 和 2；遇到 v1 时把 closed_at 读作 NULL（查询按版本选用 `closed_at` 或 `NULL`）。**读路径从不迁移**：Settings 打开、Telemetry 页、Drover 读取报告都保持只读。
- **写**：
  - `writer()` 打开 v1 库时，在同一个 IMMEDIATE 事务内复核 user_version，然后加列、建三个触发器、设 user_version=2。两个进程并发迁移时，后到者读到 2 就跳过。
  - 迁移共用现有 100 ms 等锁预算；失败就回滚并返回 unavailable，各业务入口按“存储不可用”处理，不重放。
  - 新二进制的任何写连接都会触发迁移，包括随后因总开关关闭而返回 disabled 的调用；迁移只改结构，不写记录。
- **不重写历史**：既有的行、事件、正文和链接都不改。历史 trace 的 closed_at=NULL，即“未结束”；历史 closure note 不会被解释为结束。本设计和部署都不操作 Theme 等历史 trace。
- **实现注意**：`create_trace` 现在用位置式 `INSERT INTO traces VALUES(?,?,?,1,0,…)`（`src/telemetry/storage.rs:254`），加列后必须改为按列名插入。

### 3.2 旧二进制的限制

- 迁移后，旧二进制（只接受 v1）读写都返回 unavailable（unsupported database version）：旧 Settings 显示 Unknown，旧 Telemetry 页报错，旧 Drover 回到 no_context 直接发送，旧 `saddle agent`/plugin 采集 unavailable 而业务照常执行一次。数据不受损。
- 迁移那一刻已经打开连接的旧进程：之后向已结束 trace 的写入被触发器拒绝；按位置向 traces 插入会因列数不符而失败。两者都表现为 unavailable，不会留下写了一半的记录。
- 不提供降级迁移。退回旧版时，要么接受遥测不可用，要么恢复迁移前的一致性快照（快照之后的新记录会丢失）。

### 3.3 实际部署顺序（需另行授权；本设计核对不是安装授权）

1. 宿主（Store v2、close、查询与显示）、Drover close、技能 revision 3 和文档按第 6 节合并后一起交付；不先发技能再发命令。
2. 用户退出日常 Saddle，并确认没有进行中的 `saddle agent`/`plugin run` 记录调用。
3. 必须备份：旧宿主和 Drover 包，以及按备份边界取得的遥测库一致性快照（SQLite backup；正文不可变，无需处理）。部署说明写明 3.2 的旧版限制。
4. 可选：在快照副本上用新二进制（临时 XDG_STATE_HOME）验证——v1 可只读访问，第一次写入后迁移到 2，历史 trace 的 closed_at 为 null，历史 closure 仍是 note。不为验证去写真实库。
5. 成套替换宿主和 Drover 包，然后启动 Saddle。已启用的 dispatch 插件会在启动时把自有且未改动的 corral-dispatch 从 revision 2 升级到 3；`saddle plugin status dispatch` 应显示两个目标 owned_current、revision 3。被改动或有冲突的目标只报告、不覆盖，用户处理后再执行 Sync resources。
6. 真实库在下一次正常写入时迁移；部署本身不为验证而写库。
7. 已在运行的主控会话不会自动刷新已加载的文本。项目 AGENTS 规定“本链路选择记录时先读遥测操作.md”，所以下次选择记录时会读到 revision 3。部署前已在记录、未按新规结束的链路保持开放并在查询页显示，可事后按 ID 结束。

## 4. 口头链路与 Tasks run 的衔接

**两种授权来源分开**：

- Tasks 的项目默认（`TELEMETRY_RECORD`）和派发时的本次覆盖，是用户已批准的记录选择，作用在每个 Tasks run 上，本设计不改。
- 口头的一次要求，覆盖的是用户这次所指的任务。
- 本次修的是“口头一次授权被后续独立任务继承”，不借此重做 Tasks 的记录选择。

| 场景 | 谁建 trace | 主控段 | 人工验收/退回段 | 谁结束、何时 |
|---|---|---|---|---|
| 口头任务，没有 Tasks run | 用户明确要求后，主控建 ad_hoc trace | 委派、执行、同任务返工、审查、closure note | 用户对同一任务的后续决定（如是否合并）由主控在同一 trace 转录 | 主控，在任务完成并交付后 |
| Tasks run，派发时按项目默认或本次覆盖选了记录 | Drover（现有 04B） | 用交付附段里的上下文记录；同 run 内的实现/审查返工都留在本 trace；收尾写 closure note，不结束链路 | Submit/Accept/Return：Drover 业务落盘后追加 task.transition，Return 带原因正文 | Drover，在 Accept 或 Return 的 transition 尝试之后 |
| Tasks run 没选记录，用户中途口头明确要求记录 | 主控经 Drover 公开接口核实 task/run 后，建 origin=task、带完整 binding 的 trace（coverage_start 是实际开始记录的时间） | 同上 | Drover 按完整 binding 找到该 trace 并追加 | Drover |
| Return 之后再派发（新 run） | 按 Tasks 已有规则：新 run 按项目默认或本次覆盖决定，选了记录就由 Drover 建新 trace；用户对新 run 口头明确要求继续记录时，属于已有的显式要求，主控按上一行绑定新 run，不需要再问一次许可 | 在新 trace 记录；需要时用 evidence.reused 显式引用旧需求 | 旧 run 的退回原因在旧 run 的 transition 中（如果写入成功），原始原因始终在 Drover 的退回历史中 | 新 run 的 Accept/Return |

**两种返工**：

- **同 run 返工**：同一 run 在 Accept/Return 之前的返工，包括主控审查后要求实现者改、交叉审查后返工、用户在 awaiting_release 期间口头要求修改但没有 Return。它们都属于本任务，留在同一 trace，用 redispatch 派发和 send_kind=rework 表达。
- **Return 后的新 run**：Return 终止这个 run，Drover 结束其 trace。之后的再派发是新 run 新 trace，是否记录按 Tasks 的项目默认或本次覆盖决定，或者由用户对新 run 的口头明确要求决定。

**剩余边界**（只列出，不建议改变 Tasks 默认值）：一个口头要求记录、绑定在某个 Tasks run 上的任务，被 Return 后以未勾选 Record 的方式再派发，而用户对新 run 没有任何口头要求时，新 run 不记录。这是 Tasks 已批准选择的直接结果。如果主控或用户认为这不符合“记录到任务完成”，需要另行决定；本设计不自行扩展。

**Drover 结束顺序**：

- 业务落盘 → 尝试追加 transition（Return 附原因）→ close。
- transition 因存储故障、预算耗尽或链路已结束等原因没写进去时，这条流转和退回原因在遥测中会永久缺失（结束后不能补交）。业务上的原始原因仍保存在 Drover 自己的数据和 Run details 的退回历史里。遥测缺口在结果中报告，不重试、不重放业务。
- 无论 transition 结果如何都尝试 close：run 已经终结，保持开放只会留下可被误用的窗口。
- 找不到该 run 的 trace（not_recorded）或查询失败时，不 close，`telemetry.close` 记 not_attempted。

**预算与结果**：close 使用单独的 300 ms 预算（与身份创建预算一致），在现有 transition 之后、返回结果之前执行。结果另加 `telemetry.close`（stored/duplicate/disabled…/not_attempted），失败明确报告；不改 delivery/record，不重试，也不改状态机、队列动作或通知。

**口头任务不要求登记 Tasks**：只有本来就存在 Drover run 时才绑定它。如果主控对已有的 Drover run 另建 ad_hoc trace，Drover 找不到它，人工流转就记不下来，所以技能要求“有 run 就绑定 run”。

## 5. dispatch 技能与遥测操作说明

修改 `plugins/dispatch/resources/corral-dispatch/` 下两个文件，revision 从 2 升到 3：

- **SKILL.md 第 10 行附近**：一次口头记录要求只覆盖用户所指的当前任务（含委派、执行、同任务返工、审查与实际收尾）；任务完成并交付后，按遥测操作.md 结束本链路；下一项独立任务未再次要求就不记录，再要求就新建 trace。Tasks 的项目默认和本次覆盖仍按 Tasks 规则处理。
- **SKILL.md 第 7 节末条**：收尾记录写完后结束链路。未绑定任务的由主控执行 `trace close`；绑定 Tasks 运行的由 Tasks 在验收或退回后结束，主控不代为结束。之后不再把本次上下文带给后续命令。
- **遥测操作.md**
  - §1 增加：
    - 授权范围、结束条件（任务完成并交付，阶段产出不是终点，同任务待决时不结束）和“任务”的含义（不是会话、项目或主题）；
    - 不需要用户说“停止记录”，也不需要用户提供 ID；
    - 不得复用已结束的 trace；
    - 两种返工的区分（见第 4 节）。
  - §2 增加：
    - 有 Drover run 时绑定该 run：已有附段就直接复用；中途口头要求记录，则核实后建 origin=task。没有 run 时用 ad_hoc。
    - 记录上下文要可恢复：项目里已有本任务的任务文件或交接文件时，可在其中记下 trace_id，结束后记“本次记录授权已结束”；没有时，放在主控为本次自建的记录目录里。不强制先建任务文件。
    - 会话压缩或重启后据此恢复，不按最新 trace 猜。
  - §6 改写“实际收尾”：
    - 先等本任务自己发起的公开调用返回，自己开的会话按项目正常生命周期处理；不为 close 停止主控或用户的 agent。
    - 然后 append closure note（派发级或 trace 级都只是声明），再对 ad_hoc trace 执行 `saddle telemetry trace close --input`（给出 JSON 示例），回执为 stored 或 duplicate 即表示已结束；origin=task 的不调用。
    - 同任务待决时不结束。
    - 结束后，后续命令不再携带这些 ID。记录文件可保留供审计，不删除任何用户材料；会话恢复时，不把已结束的 trace 当作可以续写的链路。
  - §7 回执：disabled 且 code=trace_closed 表示链路已结束；纯记录不重交，执行入口的业务结果不受影响、不重发。无效上下文仍会被拒绝，这与链路是否结束无关。close 返回 invalid（例如宿主不支持该命令）时报告“未能结束”，不得以重做业务来补救。
- **`plugins/dispatch/src/lib.rs`**：revision 改为 3，同时更新 `revision_and_original_template_are_pinned_to_bytes` 中的指纹。项目AGENTS模板.md 不改，它单独的哈希断言保持不变。资源 README.md 没有必要就不改。
- **升级**：资源随同版本二进制嵌入，按 03B 已定的生命周期，在启动时升级自有且未改动的 revision 2；status 会区分 owned_outdated 和 modified。用户无需新设置；项目 AGENTS 模板和本仓库 AGENTS 的那一行都可以不改（那一行已经要求选择记录时先读遥测操作.md）。
